\chapter{เนื้องาน}\label{ch:impl}

\section{โครงสร้างโปรเจกต์}\label{sec:impl-structure}

โค้ดทั้งหมดเขียนด้วย Python 3.13 บริหารจัดการ dependency ด้วย \texttt{uv}
แบ่งเป็นห้าส่วนตามหน้าที่:

\begin{itemize}[leftmargin=1.6em]
\item \texttt{attackpath/} -- แพ็กเกจหลัก: โมเดลกราฟ (\texttt{graph.py}), ตัวสร้างกราฟจำลอง
(\texttt{gen.py}), การให้น้ำหนัก (\texttt{weights.py}), ตัววิเคราะห์จุดตัด
(\texttt{chokepoints.py}), การทดสอบความทนทาน (\texttt{robustness.py}) และสคีมา
ผลลัพธ์ (\texttt{results.py}) -- ไม่พึ่ง Neo4j เลยแม้แต่บรรทัดเดียว (หัวข้อ~\ref{sec:impl-analyzer})
\item \texttt{experiments/} -- ตัวขับเคลื่อนการทดลองทั้งเจ็ดชุด (\texttt{run.py}), การ
วิเคราะห์ผลเป็นตารางและกราฟ (\texttt{analyze.py}) และ exp 6 ที่แยกสคริปต์ต่างหาก
\item \texttt{scripts/} -- ท่อประมวลผลข้อมูล (ดึง EPSS/NVD, fit, ตรวจสอบ rubric, ตรวจสอบ
คำกล่าวอ้างในเอกสาร)
\item \texttt{lab/} -- Terraform, docker-compose ของ on-prem และตัว export จาก Neo4j
\item \texttt{tests/} -- ชุดทดสอบ 70 ไฟล์ย่อย (หัวข้อ~\ref{sec:impl-tests})
\end{itemize}

\section{ท่อประมวลผลข้อมูลและการ fit}\label{sec:impl-pipeline}

ข้อมูลที่ใช้ fit ฟังก์ชัน CVSS$\to$EPSS มาจากการดึงสองแหล่งแล้ว join กัน (\texttt{scripts/
pull\_data.py}): คะแนน EPSS ทั้งหมด ณ วันที่กำหนด (ไฟล์ snapshot จาก
\texttt{epss.empiricalsecurity.com}) และเวกเตอร์ CVSS v3.1/v3.0 จาก NVD API 2.0
ดึงเป็นบล็อกละ 2{,}000 รายการ แคชทุกบล็อกลงดิสก์ถาวรเพื่อให้รันซ้ำได้โดยไม่ดึงซ้ำ
ผลคือ CVE ที่มีทั้งเวกเตอร์และ EPSS พร้อมกัน 46{,}543 รายการ หลังตัด CVE ที่เผยแพร่
ก่อนปี 2016 ออก (ปีที่ CVSS v3 เริ่มใช้งานจริงอย่างเป็นระบบ) เหลือ 46{,}360 รายการที่
เข้า fit (\texttt{scripts/fit\_weights.py}) โมเดลที่ใช้ตั้งราคา edge จริงคือการถดถอยเชิงเส้น
จาก 8 ตัวแปรของ CVSS (AV/AC/PR/UI/S/C/I/A แบบ one-hot) ในสเกล logit ของ EPSS
ซึ่งให้ค่าสัมประสิทธิ์ที่ตรวจสอบย้อนกลับได้ทีละตัวแปร

\section{ตัววิเคราะห์จุดตัด}\label{sec:impl-analyzer}

ตัววิเคราะห์ (\texttt{chokepoints.py}, \texttt{robustness.py}) อ่านกราฟจากไฟล์ edge list
ธรรมดา (JSON หรือ CSV) เท่านั้น ไม่เรียก Neo4j driver แม้แต่บรรทัดเดียว เพื่อให้กราฟจำลอง
และกราฟจาก lab จริงไหลผ่านโค้ดวิเคราะห์ตัวเดียวกันโดยไม่ต้องแก้โค้ด (ซึ่งเป็นเงื่อนไขของ
วัตถุประสงค์ข้อ 5 (หัวข้อ~\ref{sec:intro-objectives}): ต้องพิสูจน์ว่าโมเดลใช้กับระบบจริงได้ ไม่ใช่ใช้ได้เฉพาะข้อมูลที่ออกแบบมาเอง)
การเชื่อมต่อกับ Neo4j ทั้งหมดถูกจำกัดไว้ในเฟส lab เท่านั้น (\texttt{lab/exporter/
export\_graph.py}, หัวข้อ~\ref{sec:impl-lab}) ซึ่งทำหน้าที่แปลงผลสืบค้น Cypher จาก Cartography ให้เป็น edge list
สคีมาเดียวกับที่ตัวสร้างกราฟจำลองสร้าง

\section{การทำซ้ำผลได้ (Reproducibility)}\label{sec:impl-repro}

กราฟจำลองทุกกราฟต้องทำซ้ำได้จาก seed เดียวกัน ซึ่งในทางปฏิบัติพบปัญหาจริงสามจุด
ระหว่างการพัฒนาและแก้ไขแล้ว:

\begin{enumerate}[leftmargin=1.6em]
\item \textbf{การเรียงลำดับของ \texttt{set} ไม่แน่นอน} ขั้นตอนซ่อมกราฟขั้นสุดท้าย (เมื่อไม่มี
ทางซ่อมอื่นเหลือ) เคยเลือก node ปลายทางด้วย \texttt{next(iter(...))} บนออบเจกต์
\texttt{set} ซึ่งลำดับขึ้นกับการสุ่มแฮชสตริงของ Python ต่อโปรเซส (\texttt{PYTHONHASHSEED})
ทำให้กราฟ seed เดียวกันต่างกันได้ระหว่างสองรัน แก้ด้วยการ \texttt{sorted()} ก่อนเลือกเสมอ
\item \textbf{\texttt{hash()}} การถ่วงน้ำหนักแต่ละโมเดลเคยใช้ \texttt{seed + hash(model) \%
1000} เพื่อให้แต่ละโมเดลน้ำหนักได้ seed ย่อยต่างกัน แต่ \texttt{hash()} ของสตริงใน Python
สุ่มต่อโปรเซสเช่นกัน แก้ด้วย \texttt{zlib.crc32()} ซึ่งให้ค่าคงที่เสมอ
\item \textbf{ไฟล์ผลลัพธ์ถูกต่อท้าย (append) โดยไม่ตั้งใจ} \texttt{Writer} เปิดไฟล์
\texttt{results/exp*.csv} แบบ append เพื่อให้เขียนหัวตารางครั้งเดียว แต่เมื่อรันกริดใหม่ทับ
ของเก่าที่ยังไม่ลบ แถวเก่ากับใหม่จะปนกัน (เคยเกิดขึ้นจริงสองครั้งระหว่างการพัฒนา) แก้ด้วย
การเช็กก่อนรันว่ามีไฟล์เดิมอยู่หรือไม่ ถ้ามีให้หยุดและต้องใช้ \texttt{--force} เพื่อลบก่อนรันใหม่
\end{enumerate}

ทั้งสามจุดตรวจพบโดยการรันตัวสร้างกราฟ/ตัวทดลองซ้ำข้ามค่า \texttt{PYTHONHASHSEED}
หลายค่าแล้วเทียบไฟล์ผลลัพธ์ว่าเหมือนกันทุกบิตหรือไม่ (วิธีนี้กลายเป็นขั้นตอนมาตรฐานก่อน
รันกริดเต็มทุกครั้งหลังจากนี้) นอกจากนี้ \texttt{git\_rev} ที่บันทึกในทุกแถวผลลัพธ์ยังต่อท้าย
\texttt{+dirty} เมื่อโค้ดที่ผลิตผลนั้นมีการแก้ไขที่ยังไม่ \texttt{commit} เพื่อไม่ให้แถวผลลัพธ์
อ้างว่ามาจาก commit ที่ไม่ได้ผลิตมันจริง

\section{Lab: Terraform, Cartography, Neo4j}\label{sec:impl-lab}

ฝั่งคลาวด์ใช้ Terraform สร้างทรัพยากรจริงบน LocalStack (community, ไม่ต้องมีบัญชี AWS
จริง -- ดูเหตุผลในภาคผนวก~\ref{app:deviation}) แล้วรัน Cartography เพื่อดึงทรัพยากรนั้นเข้า Neo4j
\texttt{lab/run\_sync.py} ครอบ CLI ของ Cartography ไว้ชั้นหนึ่งเพื่อ monkeypatch เฉพาะ
ฟังก์ชันเดียว (\texttt{iam.sync\_service\_last\_accessed\_details}) ที่ LocalStack community
ไม่รองรับและทำให้ทั้งขั้นตอนค้าง -- ไม่ใช่การเขียน collector ขึ้นใหม่แทน Cartography
ซึ่งอยู่นอกขอบเขตของโครงงาน (หัวข้อ~\ref{sec:intro-scope})

ฝั่ง on-prem จำลองด้วย \texttt{docker-compose} สองเครื่องบนเครือข่าย flat เดียวกัน
(ซึ่ง\emph{คือ}ตัว misconfig \texttt{flat-vlan-no-segmentation} เอง ไม่ใช่ทางลัดข้ามการ
จำลองมัน) \texttt{lab/exporter/onprem.py} ยืนยันว่าทั้งสองโฮสต์เปิดพอร์ต SSH จริงด้วย
\texttt{nmap} แล้วลองเจาะรหัสผ่าน root ด้วย dictionary attack จริงผ่าน \texttt{paramiko}
ก่อนจะอนุญาตให้ edge \texttt{aws-key-on-host} ปรากฏในกราฟ -- ถ้าเจาะไม่สำเร็จจะไม่มี
edge ให้สิทธิ์ผ่านมา ป้องกันไม่ให้กราฟกระโดดข้ามขั้นที่ผู้โจมตีต้องมี shell จริงก่อน

edge ข้ามโดเมนเส้นเดียวของกราฟ lab (\texttt{aws-key-on-host}) ต้องการหลักฐานจาก
\emph{สองแหล่งอิสระ}ที่ตรงกัน: รหัส access key ที่อ่านจากไฟล์บนคอนเทนเนอร์ on-prem จริง
ต้องตรงกับ \texttt{AccountAccessKey} node ที่ Cartography ค้นพบเองจากฝั่งคลาวด์ หาก
ไม่ตรงกัน \texttt{export\_graph.py} จะปฏิเสธสร้าง edge นั้นทันที (ทดสอบแล้วด้วยการแก้ไข
รหัสบนโฮสต์ให้ไม่ตรงกับฝั่งคลาวด์โดยตั้งใจ -- ดูหัวข้อ~\ref{sec:eval-lab}) ออกแบบเช่นนี้เพื่อให้ edge
ข้ามโดเมนเป็นการค้นพบที่เกิดจากข้อมูลจริงสองฝั่งเห็นพ้องกัน ไม่ใช่ข้อเท็จจริงที่ปลูกไว้
ฝ่ายเดียวแล้วอ้างว่าเป็นการค้นพบ

\section{การทดสอบซอฟต์แวร์}\label{sec:impl-tests}

ชุดทดสอบมี 2{,}171 กรณี ผ่านทั้งหมด แบ่งเป็นสองชั้น ชั้นแรกคือเทสต์หน่วยปกติ
(\texttt{test\_gen.py}, \texttt{test\_dominator.py}, \texttt{test\_nodecut.py},
\texttt{test\_weights.py}, \texttt{test\_robustness.py}, \texttt{test\_cross\_share.py})
ตรวจคุณสมบัติเฉพาะจุด เช่น ความเท่ากันของ post-dominator กับ pairwise-dominator,
min-cut คืนเซต node ไม่ใช่ edge, คู่ที่ไปไม่ถึงกันถูกข้ามไม่ใช่นับเป็นเซตว่าง

ชั้นที่สองคือ \texttt{test\_bruteforce.py} ซึ่งเทียบผลของตัววิเคราะห์กับคำตอบที่คำนวณจาก
นิยามตรง ๆ (ไม่เรียกโค้ดที่กำลังตรวจสอบ) บนกราฟสุ่มขนาดเล็ก 300 กราฟ ครอบคลุมทั้ง
dominator (ทั้งสามนิยาม), ความเหมาะสมที่สุดของ weighted node min-cut (ทั้งสามสเกล
capacity, เทียบกับการไล่ทุกเซตย่อยของ node) และคะแนน $\Delta(v)$ (คำนวณใหม่ด้วย
Dijkstra ล้วน ๆ ทีละ node) ความถูกต้องของชุดทดสอบนี้เองถูกยืนยันด้วยการฉีดบั๊กจริงสาม
แบบเข้าไปในโค้ด (ตัวกรอง candidate ทิ้ง node สำคัญ, min-cut ไม่สนใจ capacity ที่ระบุ,
นับคู่ที่ไปไม่ถึงกันเป็นเซตว่าง) แล้วยืนยันว่าชุดทดสอบจับผิดได้ทั้งสามแบบ ก่อนนำบั๊กออก
