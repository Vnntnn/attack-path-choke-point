\section{โครงสร้างโปรเจกต์}\label{sec:impl-structure}

โค้ดทั้งหมดเขียนด้วย Python 3.13 บริหารจัดการ dependency ด้วย \texttt{uv} และแบ่งเป็น
ห้าส่วนตามหน้าที่ ดังนี้

\begin{itemize}[leftmargin=1.6em]
\item \texttt{attackpath/} -- แพ็กเกจหลักของโครงงาน ประกอบด้วยโมเดลกราฟ
(\texttt{graph.py}), ตัวสร้างกราฟจำลอง (\texttt{gen.py}), การให้น้ำหนัก
(\texttt{weights.py}), ตัววิเคราะห์จุดตัด (\texttt{chokepoints.py}), การทดสอบความ
ทนทาน (\texttt{robustness.py}) และสคีมาผลลัพธ์ (\texttt{results.py}) แพ็กเกจนี้ไม่พึ่ง
Neo4j เลยแม้แต่บรรทัดเดียว (เหตุผลอยู่ในหัวข้อ~\ref{sec:impl-analyzer})
\item \texttt{experiments/} -- ตัวขับเคลื่อนการทดลองทั้งเจ็ดชุด (\texttt{run.py}) พร้อมตัว
วิเคราะห์ผลเป็นตารางและกราฟ (\texttt{analyze.py}) และ exp 6 ซึ่งแยกสคริปต์ต่างหาก
\item \texttt{scripts/} -- ท่อประมวลผลข้อมูลและตัวตรวจสอบ ประกอบด้วย
\texttt{pull\_data.py} (ดึง EPSS กับ CVSS มา join กัน -- รายละเอียดในหัวข้อ~
\ref{sec:impl-pipeline}), \texttt{fit\_weights.py} (ฝึกฟังก์ชัน CVSS$\to$EPSS ทั้ง 4
แบบแล้วเลือกโมเดลที่ใช้จริง), \texttt{build\_vectors.py}/\texttt{calibrate\_rubric.py}
(ตรวจและนับความครบถ้วนของ rubric misconfiguration -- ภาคผนวก~\ref{app:rubric}),
\texttt{audit\_data.py} (ตรวจสอบการ join ข้อมูลซ้ำด้วยโค้ดคนละชุดจากที่ใช้จริง) และ
\texttt{check\_claims.py} (อ่านตัวเลขทุกตัวที่ปรากฏในเอกสารฉบับนี้ แล้วคำนวณใหม่จาก
\texttt{results/}/\texttt{data/fit/} เทียบว่าตรงกันทุกตัวหรือไม่ ถ้าไม่ตรงจะแจ้งชื่อไฟล์และ
ตัวเลขที่ผิดทันที)
\item \texttt{lab/} -- ไฟล์ Terraform, docker-compose ของฝั่ง on-prem และตัว export
จาก Neo4j
\item \texttt{tests/} -- ชุดทดสอบ 70 ไฟล์ย่อย (รายละเอียดในหัวข้อ~\ref{sec:impl-tests})
\end{itemize}

\section{ท่อประมวลผลข้อมูลและการ fit}\label{sec:impl-pipeline}

ก่อนจะ fit ฟังก์ชัน CVSS$\to$EPSS ได้ ต้องมีข้อมูลที่มีทั้งสองค่าคู่กันก่อน ขั้นตอนนี้ทำโดย
\texttt{scripts/pull\_data.py} ซึ่งดึงข้อมูลสองแหล่งแล้วนำมา join กัน แหล่งแรกคือคะแนน
EPSS ทั้งหมด ณ วันที่กำหนด (ไฟล์ snapshot จาก \texttt{epss.empiricalsecurity.com})
แหล่งที่สองคือเวกเตอร์ CVSS v3.1/v3.0 จาก NVD API 2.0 ซึ่งดึงเป็นบล็อกละ 2{,}000
รายการ และแคชทุกบล็อกลงดิสก์ถาวร เพื่อให้รันซ้ำได้โดยไม่ต้องดึงใหม่ทุกครั้ง

ผลจากการ join ได้ CVE ที่มีทั้งเวกเตอร์และ EPSS พร้อมกัน 46{,}543 รายการ หลังตัด CVE
ที่เผยแพร่ก่อนปี 2016 ออก (เพราะเป็นปีที่ CVSS v3 เริ่มใช้งานจริงอย่างเป็นระบบ) เหลือ
46{,}360 รายการที่เข้า fit จริง (\texttt{scripts/fit\_weights.py}) โมเดลที่ใช้ตั้งราคา edge
จริงคือการถดถอยเชิงเส้นจาก 8 ตัวแปรของ CVSS (AV/AC/PR/UI/S/C/I/A แบบ one-hot)
ในสเกล logit ของ EPSS ซึ่งเลือกใช้รูปแบบนี้เพราะให้ค่าสัมประสิทธิ์ที่ตรวจสอบย้อนกลับได้
ทีละตัวแปร ตรงกับที่ต้องการในวัตถุประสงค์ข้อ 2

\section{ตัววิเคราะห์จุดตัด}\label{sec:impl-analyzer}

ตัววิเคราะห์ (\texttt{chokepoints.py}, \texttt{robustness.py}) ถูกออกแบบให้อ่านกราฟ
จากไฟล์ edge list ธรรมดาเท่านั้น (JSON หรือ CSV) และไม่เรียก Neo4j driver เลยแม้แต่
บรรทัดเดียว เหตุผลคือต้องการให้กราฟจำลองและกราฟจาก lab จริงไหลผ่านโค้ดวิเคราะห์ตัว
เดียวกันได้โดยไม่ต้องแก้โค้ดเลย ซึ่งเป็นเงื่อนไขของวัตถุประสงค์ข้อ 5
(หัวข้อ~\ref{sec:intro-objectives}): ต้องพิสูจน์ว่าโมเดลใช้กับระบบจริงได้ ไม่ใช่ใช้ได้เฉพาะ
ข้อมูลที่ออกแบบมาเอง ด้วยเหตุนี้ การเชื่อมต่อกับ Neo4j ทั้งหมดจึงถูกจำกัดไว้ในเฟส lab
เท่านั้น (\texttt{lab/exporter/export\_graph.py}, หัวข้อ~\ref{sec:impl-lab}) ซึ่งมีหน้าที่
เดียวคือแปลงผลสืบค้น Cypher จาก Cartography ให้กลายเป็น edge list สคีมาเดียวกับที่
ตัวสร้างกราฟจำลองสร้างขึ้นมา

\section{การทำซ้ำผลได้ (Reproducibility)}\label{sec:impl-repro}

กราฟจำลองทุกกราฟต้องทำซ้ำได้จาก seed เดียวกันเป๊ะ ซึ่งฟังดูตรงไปตรงมา แต่ระหว่างการ
พัฒนาจริงกลับพบปัญหาที่ทำให้ทำซ้ำไม่ได้ถึงสามจุด และได้แก้ไขแล้วทั้งหมด ดังนี้

\begin{enumerate}[leftmargin=1.6em]
\item \textbf{การเรียงลำดับของ \texttt{set} ไม่แน่นอน} ขั้นตอนซ่อมกราฟขั้นสุดท้าย (ใช้
เมื่อไม่มีทางซ่อมอื่นเหลือ) เคยเลือก node ปลายทางด้วย \texttt{next(iter(...))} บน
ออบเจกต์ \texttt{set} ของ Python ปัญหาคือลำดับของ \texttt{set} ขึ้นกับการสุ่มแฮชสตริง
ของ Python ต่อโปรเซส (\texttt{PYTHONHASHSEED}) ทำให้กราฟที่ใช้ seed เดียวกันกลับ
ต่างกันได้ระหว่างสองรัน แก้ไขโดยเรียก \texttt{sorted()} ก่อนเลือกเสมอ
\item \textbf{\texttt{hash()}} การถ่วงน้ำหนักแต่ละโมเดลเคยใช้ \texttt{seed +
hash(model) \% 1000} เพื่อให้แต่ละโมเดลน้ำหนักได้ seed ย่อยที่ต่างกัน แต่ \texttt{hash()}
ของสตริงใน Python สุ่มต่อโปรเซสเช่นเดียวกับปัญหาข้อแรก แก้ไขโดยเปลี่ยนไปใช้
\texttt{zlib.crc32()} ซึ่งให้ค่าคงที่เสมอไม่ว่าจะรันกี่ครั้ง
\item \textbf{ไฟล์ผลลัพธ์ถูกต่อท้าย (append) โดยไม่ตั้งใจ} \texttt{Writer} เปิดไฟล์
\texttt{results/exp*.csv} แบบ append เพื่อให้เขียนหัวตารางเพียงครั้งเดียว แต่เมื่อรันกริด
ใหม่ทับของเก่าที่ยังไม่ได้ลบไฟล์ แถวเก่ากับแถวใหม่จะปนกัน (เกิดขึ้นจริงสองครั้งระหว่างการ
พัฒนา) แก้ไขโดยให้ตรวจก่อนรันว่ามีไฟล์เดิมอยู่หรือไม่ ถ้ามีจะหยุดทันทีและต้องใช้
\texttt{--force} เพื่อลบก่อนรันใหม่เท่านั้น
\end{enumerate}

ทั้งสามจุดนี้ตรวจพบด้วยวิธีเดียวกัน คือรันตัวสร้างกราฟหรือตัวทดลองซ้ำข้ามค่า
\texttt{PYTHONHASHSEED} หลายค่า แล้วเทียบไฟล์ผลลัพธ์ว่าเหมือนกันทุกบิตหรือไม่ วิธีนี้
กลายเป็นขั้นตอนมาตรฐานก่อนรันกริดเต็มทุกครั้งหลังจากนี้ นอกจากนี้ \texttt{git\_rev} ที่
บันทึกไว้ในทุกแถวผลลัพธ์ยังต่อท้ายด้วย \texttt{+dirty} เมื่อโค้ดที่ผลิตผลนั้นมีการแก้ไขที่ยัง
ไม่ได้ \texttt{commit} เพื่อป้องกันไม่ให้แถวผลลัพธ์อ้างว่ามาจาก commit ที่จริง ๆ แล้วไม่ได้
ผลิตมันขึ้นมา

\section{Lab: Terraform, Cartography, Neo4j}\label{sec:impl-lab}

ฝั่งคลาวด์ของ lab ใช้ Terraform สร้างทรัพยากรจริงบน LocalStack (เวอร์ชัน community
ซึ่งไม่ต้องมีบัญชี AWS จริง -- เหตุผลเต็มอยู่ในภาคผนวก~\ref{app:deviation}) แล้วรัน
Cartography เพื่อดึงทรัพยากรที่สร้างนั้นเข้า Neo4j \texttt{lab/run\_sync.py} ครอบ CLI
ของ Cartography ไว้อีกชั้นหนึ่ง เพื่อ monkeypatch เฉพาะฟังก์ชันเดียว
(\texttt{iam.sync\_service\_last\_accessed\_details}) ที่ LocalStack community ไม่
รองรับและทำให้ทั้งขั้นตอนค้าง การทำแบบนี้ไม่ใช่การเขียน collector ขึ้นใหม่แทน
Cartography ซึ่งอยู่นอกขอบเขตของโครงงาน (หัวข้อ~\ref{sec:intro-scope}) แต่เป็นการแก้
จุดบกพร่องเล็ก ๆ จุดเดียวเท่านั้น

ฝั่ง on-prem จำลองด้วย \texttt{docker-compose} สองเครื่องบนเครือข่าย flat เดียวกัน ซึ่ง
การไม่แบ่งเครือข่ายแบบนี้\emph{คือ}ตัว misconfig \texttt{flat-vlan-no-segmentation}
เอง ไม่ใช่ทางลัดข้ามการจำลองมัน \texttt{lab/exporter/onprem.py} ยืนยันก่อนว่าทั้งสอง
โฮสต์เปิดพอร์ต SSH จริงด้วย \texttt{nmap} (เครื่องมือสแกนพอร์ตเครือข่ายมาตรฐาน บอกได้ว่า
เครื่องเป้าหมายเปิดบริการอะไรอยู่บ้าง โดยไม่บอกว่ามีช่องโหว่อะไร) แล้วลองเจาะรหัสผ่าน
root ด้วย dictionary attack (ลองรหัสผ่านที่พบบ่อยในฐานข้อมูลรหัสผ่านที่เคยหลุดจริง
ทีละตัวจนกว่าจะเข้าได้หรือหมดรายการ) จริงผ่าน \texttt{paramiko} (ไลบรารี Python
สำหรับเชื่อมต่อ SSH แบบเขียนโค้ดสั่งการได้ ใช้แทนการพิมพ์คำสั่ง \texttt{ssh} เอง) ก่อน
จะอนุญาตให้ edge \texttt{aws-key-on-host}
ปรากฏในกราฟได้ ถ้าเจาะไม่สำเร็จจะไม่มี edge ให้สิทธิ์ผ่านมาเลย เพื่อป้องกันไม่ให้กราฟ
กระโดดข้ามขั้นที่ผู้โจมตีต้องมี shell จริงก่อน

edge ข้ามโดเมนเส้นเดียวของกราฟ lab (\texttt{aws-key-on-host}) ยังต้องการหลักฐานจาก
\emph{สองแหล่งอิสระ}ที่ตรงกันอีกด้วย กล่าวคือ รหัส access key ที่อ่านได้จากไฟล์บน
คอนเทนเนอร์ on-prem จริง ต้องตรงกับ \texttt{AccountAccessKey} node ที่
Cartography ค้นพบเองจากฝั่งคลาวด์ หากไม่ตรงกัน \texttt{export\_graph.py} จะปฏิเสธ
สร้าง edge นั้นทันที (ทดสอบจริงแล้วด้วยการแก้ไขรหัสบนโฮสต์ให้ไม่ตรงกับฝั่งคลาวด์โดย
ตั้งใจ -- ดูหัวข้อ~\ref{sec:eval-lab}) การออกแบบแบบนี้ทำให้ edge ข้ามโดเมนเป็นการค้นพบ
ที่เกิดจากข้อมูลจริงสองฝั่งเห็นพ้องต้องกัน ไม่ใช่ข้อเท็จจริงที่ปลูกไว้ฝ่ายเดียวแล้วอ้างว่าเป็น
การค้นพบ

\section{การทดสอบซอฟต์แวร์}\label{sec:impl-tests}

ชุดทดสอบทั้งหมดมี 2{,}171 กรณี และผ่านทั้งหมด แบ่งเป็นสองชั้นที่ตรวจคนละเรื่อง ชั้นแรก
คือเทสต์หน่วยปกติ (\texttt{test\_gen.py}, \texttt{test\_dominator.py},
\texttt{test\_nodecut.py}, \texttt{test\_weights.py}, \texttt{test\_robustness.py},
\texttt{test\_cross\_share.py}) ซึ่งตรวจคุณสมบัติเฉพาะจุดของแต่ละฟังก์ชัน เช่น ความ
เท่ากันของ post-dominator กับ pairwise-dominator, min-cut ต้องคืนเซต node ไม่ใช่
edge, คู่ที่ไปไม่ถึงกันต้องถูกข้ามไม่ใช่นับเป็นเซตว่าง

ชั้นที่สองคือ \texttt{test\_bruteforce.py} ซึ่งตรวจอีกระดับหนึ่ง: แทนที่จะตรวจคุณสมบัติ
เฉพาะจุด มันเทียบผลของตัววิเคราะห์กับคำตอบที่คำนวณขึ้นใหม่จากนิยามตรง ๆ (ไม่เรียกโค้ด
ที่กำลังตรวจสอบเลย) บนกราฟสุ่มขนาดเล็ก 300 กราฟ ครอบคลุมทั้งสาม dominator (ทั้งสาม
นิยาม), ความเหมาะสมที่สุดของ weighted node min-cut (ทั้งสามสเกล capacity เทียบกับ
การไล่ทุกเซตย่อยของ node) และคะแนน $\Delta(v)$ (คำนวณใหม่ด้วย Dijkstra ล้วน ๆ ทีละ
node) เพื่อให้มั่นใจว่าชุดทดสอบนี้เองตรวจจับบั๊กได้จริง ไม่ใช่แค่ผ่านเฉย ๆ จึงทดลองฉีดบั๊ก
จริงสามแบบเข้าไปในโค้ด (ตัวกรอง candidate ทิ้ง node สำคัญ, min-cut ไม่สนใจ capacity
ที่ระบุ, นับคู่ที่ไปไม่ถึงกันเป็นเซตว่าง) แล้วยืนยันว่าชุดทดสอบจับผิดได้ครบทั้งสามแบบ ก่อนจะ
นำบั๊กที่ฉีดเข้าไปออก
