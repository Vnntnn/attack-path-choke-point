\section{โครงสร้างโปรเจกต์}\label{sec:impl-structure}

โค้ดทั้งหมดเขียนด้วย Python 3.13 บริหารจัดการ dependency ด้วย \texttt{uv} และแบ่งเป็น
ห้าส่วนตามหน้าที่ ดังนี้

\begin{itemize}[leftmargin=1.6em]
\item \texttt{attackpath/} -- แพ็กเกจหลักของโครงงาน ประกอบด้วยโมเดลกราฟ
(\texttt{graph.py}), ตัวสร้างกราฟจำลอง (\texttt{gen.py}), การให้น้ำหนัก
(\texttt{weights.py}), ตัววิเคราะห์จุดตัด (\texttt{chokepoints.py}), การทดสอบความ
ทนทาน (\texttt{robustness.py}) และสคีมาผลลัพธ์ (\texttt{results.py}) แพ็กเกจนี้ไม่พึ่ง
Neo4j เลยแม้แต่บรรทัดเดียว เหตุผลอยู่ในหัวข้อ~\ref{sec:impl-analyzer}
\item \texttt{experiments/} -- ตัวขับเคลื่อนการทดลองทั้งเจ็ดชุด (\texttt{run.py}) พร้อมตัว
วิเคราะห์ผลเป็นตารางและกราฟ (\texttt{analyze.py}) และ exp 6 ซึ่งแยกสคริปต์ต่างหาก
\item \texttt{scripts/} -- ท่อประมวลผลข้อมูลและตัวตรวจสอบ \texttt{pull\_data.py}
ดึง EPSS กับ CVSS มา join กัน (รายละเอียดในหัวข้อ~\ref{sec:impl-pipeline})
\texttt{fit\_weights.py} ฝึกฟังก์ชัน CVSS$\to$EPSS ทั้ง 4 แบบแล้วเลือกโมเดลที่ใช้จริง
\texttt{build\_vectors.py} กับ \texttt{calibrate\_rubric.py} ตรวจและนับความครบถ้วน
ของ rubric misconfiguration (ภาคผนวก~\ref{app:rubric}) \texttt{audit\_data.py}
ตรวจสอบการ join ข้อมูลซ้ำด้วยโค้ดคนละชุดจากที่ใช้จริง ส่วน \texttt{check\_claims.py}
อ่านตัวเลขทุกตัวที่ปรากฏในเอกสารฉบับนี้ แล้วคำนวณใหม่จาก \texttt{results/} กับ
\texttt{data/fit/} ว่าตรงกันทุกตัวหรือไม่ ถ้าไม่ตรงจะแจ้งชื่อไฟล์และตัวเลขที่ผิดทันที
\item \texttt{lab/} -- ไฟล์ Terraform, docker-compose ของฝั่ง on-prem และตัว export
จาก Neo4j
\item \texttt{tests/} -- ชุดทดสอบ 70 ไฟล์ย่อย (รายละเอียดในหัวข้อ~\ref{sec:impl-tests})
\end{itemize}

\section{ท่อประมวลผลข้อมูลและการ fit}\label{sec:impl-pipeline}

ก่อนจะ fit ฟังก์ชัน CVSS$\to$EPSS ได้ ต้องมีข้อมูลที่มีทั้งสองค่าคู่กันก่อน ขั้นตอนนี้ทำโดย
\texttt{scripts/pull\_data.py} ซึ่งดึงข้อมูลสองแหล่งแล้วนำมา join กัน แหล่งแรกคือคะแนน
EPSS ทั้งหมด ณ วันที่กำหนด (ไฟล์ snapshot จาก \texttt{epss.empiricalsecurity.com})
แหล่งที่สองคือเวกเตอร์ CVSS v3.1/v3.0 จาก NVD API 2.0 ซึ่งดึงเป็นบล็อกละ 2{,}000
รายการ และแคชทุกบล็อกลงดิสก์ถาวร เพื่อให้รันซ้ำได้โดยไม่ต้องดึงใหม่ทุกครั้ง

ผลจากการ join ได้ CVE ที่มีทั้งเวกเตอร์และ EPSS พร้อมกัน 46{,}543 รายการ จากนั้นตัด
CVE ที่เผยแพร่ก่อนปี 2016 ออกไป เพราะปีนั้นคือปีที่ CVSS v3 เริ่มใช้งานจริงอย่างเป็นระบบ
เหลือ 46{,}360 รายการที่เข้า fit จริงผ่าน \texttt{scripts/fit\_weights.py} โมเดลที่ใช้ตั้ง
ราคา edge จริงคือการถดถอยเชิงเส้นจาก 8 ตัวแปรของ CVSS (AV/AC/PR/UI/S/C/I/A
แบบ one-hot) ในสเกล logit ของ EPSS เลือกใช้รูปแบบนี้เพราะให้ค่าสัมประสิทธิ์ที่ตรวจสอบ
ย้อนกลับได้ทีละตัวแปร ตรงกับที่ต้องการในวัตถุประสงค์ข้อ 2

\section{ตัววิเคราะห์จุดตัด}\label{sec:impl-analyzer}

ตัววิเคราะห์ (\texttt{chokepoints.py}, \texttt{robustness.py}) อ่านกราฟจากไฟล์ edge
list ธรรมดาเท่านั้น ไม่ว่าจะเป็น JSON หรือ CSV และไม่เรียก Neo4j driver เลยแม้แต่
บรรทัดเดียว ทำแบบนี้เพราะวัตถุประสงค์ข้อ 5 (หัวข้อ~\ref{sec:intro-objectives}) บังคับ
ให้ต้องพิสูจน์ว่าโมเดลใช้กับระบบจริงได้ ไม่ใช่ใช้ได้เฉพาะข้อมูลที่ออกแบบมาเอง กราฟจำลอง
กับกราฟจาก lab จริงจึงต้องไหลผ่านโค้ดวิเคราะห์ตัวเดียวกันได้โดยไม่ต้องแก้โค้ดสักบรรทัด
การเชื่อมต่อกับ Neo4j ทั้งหมดจึงถูกจำกัดไว้ในเฟส lab เท่านั้น นั่นคือ
\texttt{lab/exporter/export\_graph.py} (หัวข้อ~\ref{sec:impl-lab}) ไฟล์นี้ทำหน้าที่
เดียว คือแปลงผลสืบค้น Cypher จาก Cartography ให้กลายเป็น edge list สคีมาเดียวกับ
ที่ตัวสร้างกราฟจำลองสร้างขึ้นมา

\section{การทำซ้ำผลได้ (Reproducibility)}\label{sec:impl-repro}

กราฟจำลองทุกกราฟต้องทำซ้ำได้จาก seed เดียวกันเป๊ะ ฟังดูเป็นเรื่องง่าย แต่ระหว่างการ
พัฒนาจริงกลับเจอปัญหาที่ทำให้ทำซ้ำไม่ได้ถึงสามจุด ทั้งสามจุดนี้แก้ไขหมดแล้ว:

\begin{enumerate}[leftmargin=1.6em]
\item \textbf{การเรียงลำดับของ \texttt{set} ไม่แน่นอน} ขั้นตอนซ่อมกราฟขั้นสุดท้าย (ใช้
เมื่อไม่มีทางซ่อมอื่นเหลือ) เคยเลือก node ปลายทางด้วย \texttt{next(iter(...))} บน
ออบเจกต์ \texttt{set} ของ Python ปัญหาคือลำดับของ \texttt{set} ขึ้นกับการสุ่มแฮชสตริง
ของ Python ต่อโปรเซส (\texttt{PYTHONHASHSEED}) ทำให้กราฟที่ใช้ seed เดียวกันกลับ
ต่างกันได้ระหว่างสองรัน แก้ไขโดยเรียก \texttt{sorted()} ก่อนเลือกเสมอ:

\begin{quote}\small\begin{verbatim}
# before: order of co depends on PYTHONHASHSEED
dst = next(x for x in co if x != e)

# after: sorted() fixes the order every time
dst = next(x for x in sorted(co) if x != e)
\end{verbatim}\end{quote}
\item \textbf{\texttt{hash()}} การถ่วงน้ำหนักแต่ละโมเดลเคยใช้ \texttt{seed +
hash(model) \% 1000} เพื่อให้แต่ละโมเดลน้ำหนักได้ seed ย่อยที่ต่างกัน แต่ \texttt{hash()}
ของสตริงใน Python สุ่มต่อโปรเซสเช่นเดียวกับปัญหาข้อแรก แก้ไขโดยเปลี่ยนไปใช้
\texttt{zlib.crc32()} ซึ่งให้ค่าคงที่เสมอไม่ว่าจะรันกี่ครั้ง
\item \textbf{ไฟล์ผลลัพธ์ถูกต่อท้าย (append) โดยไม่ตั้งใจ} \texttt{Writer} เปิดไฟล์
\texttt{results/exp*.csv} แบบ append เพื่อให้เขียนหัวตารางเพียงครั้งเดียว แต่เมื่อรันกริด
ใหม่ทับของเก่าที่ยังไม่ได้ลบไฟล์ แถวเก่ากับแถวใหม่จะปนกัน (เกิดขึ้นจริงสองครั้งระหว่างการ
พัฒนา) แก้ไขโดยให้ตรวจก่อนรันว่ามีไฟล์เดิมอยู่หรือไม่ ถ้ามีจะหยุดทันทีและต้องใช้
\texttt{--force} เพื่อลบก่อนรันใหม่เท่านั้น
\end{enumerate}

ทั้งสามจุดนี้ตรวจพบด้วยวิธีเดียวกัน คือรันตัวสร้างกราฟหรือตัวทดลองซ้ำข้ามค่า
\texttt{PYTHONHASHSEED} หลายค่า แล้วเทียบไฟล์ผลลัพธ์ว่าเหมือนกันทุกบิตหรือไม่ วิธีนี้
กลายเป็นขั้นตอนมาตรฐานก่อนรันกริดเต็มทุกครั้งหลังจากนี้ นอกจากนี้ \texttt{git\_rev} ที่
บันทึกไว้ในทุกแถวผลลัพธ์ยังต่อท้ายด้วย \texttt{+dirty} เมื่อโค้ดที่ผลิตผลนั้นมีการแก้ไขที่ยัง
ไม่ได้ \texttt{commit} เพื่อป้องกันไม่ให้แถวผลลัพธ์อ้างว่ามาจาก commit ที่จริง ๆ แล้วไม่ได้
ผลิตมันขึ้นมา

\section{Lab: Terraform, Cartography, Neo4j}\label{sec:impl-lab}

ฝั่งคลาวด์ของ lab ใช้ Terraform สร้างทรัพยากรจริงบน LocalStack เวอร์ชัน community
ซึ่งไม่ต้องมีบัญชี AWS จริง (เหตุผลเต็มอยู่ในภาคผนวก~\ref{app:deviation}) แล้วรัน
Cartography เพื่อดึงทรัพยากรที่สร้างนั้นเข้า Neo4j \texttt{lab/run\_sync.py} ครอบ CLI
ของ Cartography ไว้อีกชั้นหนึ่ง เพียงเพื่อ monkeypatch ฟังก์ชันเดียวคือ
\texttt{iam.sync\_service\_last\_accessed\_details} ที่ LocalStack community ไม่
รองรับและทำให้ทั้งขั้นตอนค้างอยู่กับที่ การทำแบบนี้ไม่ใช่การเขียน collector ขึ้นใหม่แทน
Cartography (เรื่องนั้นอยู่นอกขอบเขตของโครงงานตามที่ระบุไว้ในหัวข้อ~\ref{sec:intro-scope})
แต่เป็นการแก้จุดบกพร่องเล็ก ๆ จุดเดียวเท่านั้น

ฝั่ง on-prem จำลองด้วย \texttt{docker-compose} สองเครื่องบนเครือข่าย flat เดียวกัน
การไม่แบ่งเครือข่ายแบบนี้\emph{คือ}ตัว misconfig \texttt{flat-vlan-no-segmentation}
เองโดยตรง ไม่ใช่ทางลัดข้ามการจำลองมัน

ก่อนจะปล่อยให้ edge \texttt{aws-key-on-host} ปรากฏในกราฟ \texttt{lab/exporter/onprem.py}
ต้องยืนยันขั้นตอนจริงสองอย่างก่อนเสมอ อย่างแรกคือสแกนด้วย \texttt{nmap} (เครื่องมือ
สแกนพอร์ตเครือข่ายมาตรฐาน บอกได้แค่ว่าเครื่องเป้าหมายเปิดบริการอะไรอยู่บ้าง ไม่บอก
ว่ามีช่องโหว่อะไร) ว่าทั้งสองโฮสต์เปิดพอร์ต SSH จริง อย่างที่สองคือลองเจาะรหัสผ่าน root
ด้วย dictionary attack จริงผ่าน \texttt{paramiko} ไลบรารี Python สำหรับสั่งงาน SSH
ด้วยโค้ด ใช้แทนการพิมพ์คำสั่ง \texttt{ssh} เอง การเจาะแบบนี้คือการลองรหัสผ่านที่พบบ่อย
ในฐานข้อมูลรหัสผ่านที่เคยหลุดจริงทีละตัว จนกว่าจะเข้าได้หรือหมดรายการ ถ้าเจาะไม่สำเร็จ
จะไม่มี edge ให้สิทธิ์ผ่านมาเลย เพื่อป้องกันไม่ให้กราฟกระโดดข้ามขั้นที่ผู้โจมตีต้องมี shell
จริงก่อน

edge ข้ามโดเมนเส้นเดียวของกราฟ lab (\texttt{aws-key-on-host}) ต้องมีหลักฐานจาก
\emph{สองแหล่งอิสระ}ที่ตรงกันด้วย: รหัส access key ที่อ่านได้จากไฟล์บนคอนเทนเนอร์
on-prem จริง ต้องตรงกับ \texttt{AccountAccessKey} node ที่ Cartography ค้นพบ
เองจากฝั่งคลาวด์ หากไม่ตรงกัน \texttt{export\_graph.py} จะปฏิเสธสร้าง edge นั้นทันที
ข้อนี้ทดสอบจริงแล้วด้วยการแก้ไขรหัสบนโฮสต์ให้ไม่ตรงกับฝั่งคลาวด์โดยตั้งใจ (ดูหัวข้อ~
\ref{sec:eval-lab}) การออกแบบแบบนี้ทำให้ edge ข้ามโดเมนเป็นการค้นพบที่เกิดจากข้อมูล
จริงสองฝั่งเห็นพ้องต้องกัน ไม่ใช่ข้อเท็จจริงที่ปลูกไว้ฝ่ายเดียวแล้วอ้างว่าเป็นการค้นพบ

\section{การทดสอบซอฟต์แวร์}\label{sec:impl-tests}

ชุดทดสอบทั้งหมดมี 2{,}171 กรณี และผ่านทั้งหมด แบ่งเป็นสองชั้นที่ตรวจคนละเรื่อง ชั้นแรก
คือเทสต์หน่วยปกติ (\texttt{test\_gen.py}, \texttt{test\_dominator.py},
\texttt{test\_nodecut.py}, \texttt{test\_weights.py}, \texttt{test\_robustness.py},
\texttt{test\_cross\_share.py}) ซึ่งตรวจคุณสมบัติเฉพาะจุดของแต่ละฟังก์ชัน เช่น ความ
เท่ากันของ post-dominator กับ pairwise-dominator, min-cut ต้องคืนเซต node ไม่ใช่
edge, คู่ที่ไปไม่ถึงกันต้องถูกข้ามไม่ใช่นับเป็นเซตว่าง

ชั้นที่สองคือ \texttt{test\_bruteforce.py} ซึ่งตรวจในอีกระดับหนึ่ง แทนที่จะตรวจคุณสมบัติ
เฉพาะจุดแบบชั้นแรก มันเทียบผลของตัววิเคราะห์กับคำตอบที่คำนวณขึ้นใหม่จากนิยามตรง ๆ
โดยไม่เรียกโค้ดที่กำลังตรวจสอบเลย ทำบนกราฟสุ่มขนาดเล็ก 300 กราฟ ครอบคลุมทั้งสาม
นิยามของ dominator ความเหมาะสมที่สุดของ weighted node min-cut ทั้งสามสเกล
capacity เทียบกับการไล่ทุกเซตย่อยของ node และคะแนน $\Delta(v)$ ที่คำนวณใหม่ด้วย
Dijkstra ล้วน ๆ ทีละ node

เพื่อให้มั่นใจว่าชุดทดสอบนี้ตรวจจับบั๊กได้จริง ไม่ใช่แค่ผ่านไปเฉย ๆ จึงลองฉีดบั๊กจริงสามแบบ
เข้าไปในโค้ด ได้แก่ตัวกรอง candidate ที่ทิ้ง node สำคัญไป, min-cut ที่ไม่สนใจ capacity
ที่ระบุ และการนับคู่ที่ไปไม่ถึงกันเป็นเซตว่าง ผลคือชุดทดสอบจับผิดได้ครบทั้งสามแบบ จึงค่อย
นำบั๊กที่ฉีดเข้าไปออก
