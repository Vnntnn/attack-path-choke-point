\section{ทฤษฎีและงานที่เกี่ยวข้อง}\label{sec:theory}
\subsection{กราฟการโจมตี (Attack Graph)}\label{sec:theory-attackgraph}

ลองนึกภาพสถานการณ์จริงสักอย่างหนึ่ง: ผู้โจมตีเจาะเข้าเครื่องหนึ่งได้สิทธิ์ผู้ใช้ทั่วไปก่อน
จากนั้นใช้ช่องโหว่อีกตัวยกระดับขึ้นเป็นสิทธิ์ผู้ดูแลระบบ แล้วอาศัยสิทธิ์นั้นไปขโมยกุญแจเข้าถึง
ระบบคลาวด์ที่หลงเหลืออยู่บนเครื่องนั้น สุดท้ายจึงเข้าถึงข้อมูลสำคัญบนคลาวด์ได้สำเร็จ แต่ละ
ขั้นตอนข้างต้นคือการ ``ขยับจากสถานะหนึ่งไปอีกสถานะหนึ่ง'' ของผู้โจมตี แนวคิดพื้นฐานของ
โครงงานนี้คือการนำลำดับขั้นตอนแบบนี้ของทั้งระบบมาวาดเป็นกราฟหนึ่งใบ โดยแทน ``สถานะที่
ผู้โจมตียืนอยู่ได้'' แต่ละแบบด้วย node หนึ่งจุด (เช่น ``มีสิทธิ์ user บนเครื่อง A'') และแทน
``การกระทำหนึ่งครั้งที่พาไปสู่สถานะถัดไป'' ด้วย edge หนึ่งเส้น (เช่น การ exploit ช่องโหว่
หนึ่งตัว) เมื่อวาดกราฟครบทั้งระบบแล้ว คำถามที่ตอบได้ทันทีคือ ``มีเส้นทางไหนบ้างที่พาผู้โจมตี
จากจุดเริ่มต้นไปถึงเป้าหมายได้'' กราฟแบบนี้เรียกว่า attack graph

แนวคิดนี้มีรากฐานจากงานของ Sheyner และคณะ~\cite{sheyner2002} พวกเขาเป็นกลุ่มแรก ๆ
ที่ทำให้คอมพิวเตอร์สร้างกราฟแบบนี้ขึ้นมาเองโดยอัตโนมัติ ป้อนข้อมูลช่องโหว่ของระบบเข้าไป
แล้วให้โปรแกรมไล่หาเส้นทางโจมตีที่เป็นไปได้ทั้งหมดออกมาเอง งานชิ้นนี้ยืมเทคนิคที่แต่เดิมใช้
ตรวจสอบว่าโปรแกรมคอมพิวเตอร์เขียนถูกต้องหรือไม่ เรียกว่า model checking มาใช้กับงาน
ความมั่นคงปลอดภัยแทน ข้อจำกัดสำคัญคือยิ่งเครือข่ายใหญ่ จำนวนเส้นทางที่เป็นไปได้ก็ยิ่งเพิ่มขึ้น
เร็วมาก วิธีนี้จึงใช้ได้จริงเฉพาะเครือข่ายขนาดเล็กเท่านั้น

ปัญหาเรื่องต้นทุนการคำนวณนี้เองที่ Ou และคณะ~\cite{ou2005} แก้ไขด้วยเครื่องมือชื่อ
MulVAL โดยเปลี่ยนไปเขียนกฎการโจมตีด้วย Datalog (ภาษาสำหรับเขียนกฎเชิงตรรกะแบบ
``ถ้า...แล้ว...'') แทนการไล่ตรวจทีละสถานะแบบเดิม ทำให้คำนวณได้เร็วขึ้นมาก งานนี้ยังเพิ่ม
แนวคิดสำคัญอีกอย่างเข้าไปในกราฟ เรียกว่า \textbf{AND-node} สำหรับกรณีที่ต้องมีหลาย
เงื่อนไขเกิดขึ้น\emph{พร้อมกัน}การโจมตีจึงจะสำเร็จ เช่น ต้องมีทั้งช่องโหว่ซอฟต์แวร์ \emph{และ}
การตั้งค่าไฟร์วอลล์ที่ผิดพลาดพร้อมกันทั้งคู่ ขาดอย่างใดอย่างหนึ่งไปก็ไปต่อไม่ได้ ต่างจาก node
ปกติที่โครงงานนี้ใช้ เรียกว่า OR-node มีทางใดทางหนึ่งสำเร็จก็ไปต่อได้แล้ว ไม่ต้องครบทุกทาง

โครงงานนี้เลือกใช้ OR-node ล้วน ไม่รองรับ AND-node เลย ตามที่ประกาศไว้ในขอบเขตของ
โครงงาน (หัวข้อ~\ref{sec:intro-scope}) เพราะทำให้คำนวณง่ายและคาดเดาเวลาที่ใช้ได้แน่นอน
กว่า (เหตุผลเชิงเทคนิคอยู่ในหัวข้อ~\ref{sec:theory-dominator}) ข้อแลกเปลี่ยนคือโครงงานนี้
แทนเงื่อนไข ``ต้องมีหลายอย่างพร้อมกัน'' แบบ AND-node ไม่ได้เลย ข้อจำกัดข้อนี้รู้ตัวมาตั้งแต่
ต้น และย้ำอีกครั้งในหัวข้อ~\ref{sec:eval-limits}

\subsection{การเสริมความมั่นคงด้วยต้นทุนต่ำสุด}\label{sec:theory-hardening}

เมื่อมีกราฟการโจมตีแล้ว คำถามที่ตามมาตามธรรมชาติคือ ``แล้วจะป้องกันอย่างไร'' สายงาน
วิจัยอีกสายหนึ่งตอบคำถามนี้ตรง ๆ ว่า ``ต้องปิดกั้นให้น้อยที่สุดกี่จุด เครือข่ายจึงจะปลอดภัยขึ้น''
Noel และคณะ~\cite{noel2003} ตอบคำถามนี้บนกราฟการโจมตี โดยมองปัญหาคล้ายกับการตัด
ถนนหรือตัดสายไฟ: หา node หรือ edge ชุดเล็กที่สุดเท่าที่จะเป็นไปได้ ที่ถ้าตัดออกแล้วผู้โจมตี
จะไปไม่ถึงเป้าหมายอีกต่อไป ปัญหาแบบนี้เรียกว่า \emph{min-cut} คือการตัดที่ต้นทุนต่ำที่สุด
โครงงานนี้นำแนวคิดนี้มาใช้โดยตรง แล้วเทียบผลกับ dominator tree (หัวข้อถัดไป) เพื่อตอบ
วัตถุประสงค์ข้อ 3 รายละเอียดอยู่ในหัวข้อ~\ref{sec:design-mincut} และ~\ref{sec:eval-cut}
สิ่งที่โครงงานนี้ต่างจากงานของ Noel คือ Noel ตัด \emph{edge} ออก ตัดเส้นทาง ส่วน
โครงงานนี้ตัด \emph{node} ออกแทน ตัดจุดยืนของผู้โจมตีเอง โดยใช้เทคนิคที่เรียกว่า
node-splitting และเปรียบเทียบผลที่ได้กับจุดตัดแบบไม่ใช้น้ำหนักเลย คือจุดตัดเชิงโครงสร้าง
ล้วน ๆ ไปพร้อมกันด้วย

\subsection{Dominator Tree}\label{sec:theory-dominator}

ลองนึกถึงเกาะที่เชื่อมกับแผ่นดินใหญ่ด้วยสะพานเพียงสะพานเดียว ไม่ว่าจะเดินทางด้วยเส้นทาง
ไหนบนเกาะนั้น ถ้าจะออกไปแผ่นดินใหญ่ก็ต้องผ่านสะพานเส้นนี้เสมอ สะพานแบบนี้คือตัวอย่าง
ที่เข้าใจง่ายที่สุดของสิ่งที่เรียกว่า \emph{dominator} วิธีที่สองที่โครงงานนี้ใช้หาจุดตัดคือ
dominator tree ตอบคำถามว่า ``node ใดบ้างที่ทุกเส้นทางจาก root ไปยัง node
เป้าหมายหนึ่ง ๆ ต้องผ่านเสมอ'' node แบบนั้นเรียกว่า dominator ของ node เป้าหมายนั้น

การหา dominator ทั้งหมดในกราฟพร้อมกันเป็นปัญหาคลาสสิกของทฤษฎีกราฟที่มีทิศทาง มี
อัลกอริทึมมาตรฐานที่คำนวณได้เร็วมากอยู่แล้ว โครงงานนี้เรียกใช้ผ่านฟังก์ชันสำเร็จรูป
\texttt{networkx.immediate\_dominators} ซึ่งมาจากงานของ Lengauer และ
Tarjan~\cite{lengauer1979} เดิมทีอัลกอริทึมนี้ถูกออกแบบมาสำหรับวิเคราะห์โปรแกรม
คอมพิวเตอร์ ไม่ใช่งานความมั่นคงปลอดภัย โดยใช้หาว่าในขั้นตอนการทำงานของโปรแกรม ซึ่ง
เขียนแทนด้วยกราฟของลำดับการทำงานของโค้ดที่เรียกว่า control-flow graph คำสั่งใดบ้าง
ที่การไหลของโปรแกรมต้องผ่านเสมอไม่ว่าจะวิ่งไปทางไหน โครงงานนี้นำอัลกอริทึมเดียวกันมาใช้
กับ attack graph แทน เพียงแค่เปลี่ยนความหมายจาก ``จุดที่โปรแกรมต้องผ่าน'' เป็น ``จุดที่
ผู้โจมตีต้องผ่าน'' เท่านั้น ตัวอัลกอริทึมเองไม่ได้เปลี่ยนแปลงอะไรเลย

\subsection{CVSS และ EPSS}\label{sec:theory-cvss-epss}

ถัดมาคือสองมาตรฐานการให้คะแนนช่องโหว่ที่โครงงานนี้ใช้สร้างความน่าจะเป็นบน edge
มาตรฐานแรกคือ Common Vulnerability Scoring System (CVSS)~\cite{cvss31} ให้คะแนน
ความรุนแรงของช่องโหว่หนึ่งรายการจากคุณสมบัติของตัวช่องโหว่เองล้วน ๆ เช่น ต้องโจมตีจาก
เครือข่ายหรือต้องอยู่เครื่องเดียวกัน ต้องมีสิทธิ์อยู่ก่อนหรือไม่ แต่ CVSS ไม่ได้บอกเลยว่า
ช่องโหว่นั้นมีโอกาสถูกใช้โจมตีจริงในโลกมากน้อยเพียงใด

CVSS เขียนคะแนนออกมาเป็นเวกเตอร์ตัวย่อ 8 ตัว โครงงานนี้อ้างถึงเวกเตอร์แบบนี้ซ้ำตลอด
ทั้งรายงาน (เช่นในรูปแบบ \texttt{AV:L/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N}) แบ่งได้เป็น
สองกลุ่มตามคำถามที่แต่ละกลุ่มตอบ กลุ่มแรกตอบว่า ``ผู้โจมตีต้องมีเงื่อนไขอะไรบ้างก่อนจะ
โจมตีสำเร็จ'':

\begin{itemize}[leftmargin=1.6em]
\item \textbf{AV} (Attack Vector) -- ต้องโจมตีจากที่ไหน: ผ่านเครือข่าย, ต้องอยู่เครื่อง
เดียวกัน, หรือต้องอยู่ใกล้ชิดทางกายภาพ
\item \textbf{AC} (Attack Complexity) -- โจมตีได้ง่าย ๆ หรือต้องมีเงื่อนไขพิเศษประกอบ
\item \textbf{PR} (Privileges Required) -- ต้องมีสิทธิ์อะไรติดตัวอยู่ก่อนแล้วบ้าง
\item \textbf{UI} (User Interaction) -- ต้องหลอกให้เหยื่อคลิกหรือทำอะไรสักอย่างด้วยหรือไม่
\end{itemize}

กลุ่มที่สองตอบคำถามต่างออกไป คือ ``ถ้าโจมตีสำเร็จแล้ว ความเสียหายกระทบไปถึงไหน'':

\begin{itemize}[leftmargin=1.6em]
\item \textbf{S} (Scope) -- ผลกระทบลามออกไปถึงทรัพยากรอื่นนอกขอบเขตเดิมหรือไม่
(\texttt{C} คือ Changed แปลว่าลามออกไป, \texttt{U} คือ Unchanged แปลว่าไม่ลาม)
\item \textbf{C/I/A} (Confidentiality/Integrity/Availability) -- ความลับ, ความถูกต้อง
และความพร้อมใช้งานของข้อมูลถูกกระทบมากน้อยแค่ไหน แต่ละด้านมีค่าเป็น \texttt{N}
(ไม่กระทบ), \texttt{L} (กระทบน้อย) หรือ \texttt{H} (กระทบมาก)
\end{itemize}

เวกเตอร์ชุดนี้คือสิ่งที่ rubric ในหัวข้อ~\ref{sec:design-rubric} ต้องกำหนดให้
misconfiguration แต่ละคลาส และเป็นตัวแปรต้น 8 ตัวที่ใช้ fit หาค่า EPSS ในหัวข้อ~
\ref{sec:impl-pipeline}

ช่องว่างตรงนี้คือสิ่งที่มาตรฐานที่สอง Exploit Prediction Scoring System
(EPSS)~\cite{jacobs2019,epss} เข้ามาเติมเต็ม โดยฝึกโมเดลทำนายจากข้อมูลการโจมตีจริง
ที่สังเกตได้ (telemetry) แล้วให้คะแนนความน่าจะเป็นว่า CVE หนึ่งรายการจะถูกใช้โจมตีจริง
ภายในกรอบเวลาหนึ่ง พูดสั้น ๆ คือสองคะแนนนี้วัดคนละเรื่องกัน: CVSS ตอบว่า ``ถ้าถูกใช้แล้ว
รุนแรงแค่ไหน'' ส่วน EPSS ตอบว่า ``มีโอกาสถูกใช้ที่ไหนสักแห่งในโลกแค่ไหน'' ข้อควรระวังคือ
EPSS ไม่ได้ตอบว่า ``มีโอกาสสำเร็จแค่ไหนเมื่อผู้โจมตียืนอยู่ต้นทางแล้ว'' นั่นเป็นคนละคำถามกัน
โดยสิ้นเชิง และเป็นเหตุผลที่โครงงานนี้ต้องสร้างฟังก์ชันแปลงค่าระหว่างสองคะแนนขึ้นมาเอง
แทนที่จะหยิบตัวใดตัวหนึ่งมาใช้แทนกันตรง ๆ (รายละเอียดวิธีแปลงอยู่ในหัวข้อ~
\ref{sec:design-pe} ผลที่ได้อยู่ในหัวข้อ~\ref{sec:eval-pe}) เหตุผลที่ต้องแปลงคือ edge ที่เป็น
misconfiguration ไม่มี CVE ผูกอยู่เลย จึงไม่มีคะแนน EPSS ให้หยิบมาใช้ได้ตรง ๆ ตั้งแต่ต้น

\subsection{เครื่องมือที่เกี่ยวข้อง}\label{sec:theory-tools}

ในเชิงอุตสาหกรรม มีเครื่องมือกลุ่ม Attack Path Management ที่ใช้แนวคิด attack graph
ในระดับใช้งานจริงอยู่แล้ว เช่น BloodHound (เน้นวิเคราะห์ Active Directory), Wiz (เน้น
คลาวด์) และ XM Cyber แต่เครื่องมือเหล่านี้มักมุ่งไปที่ฝั่งใดฝั่งหนึ่งเป็นหลัก เลือกวิเคราะห์
เฉพาะ on-prem หรือเฉพาะ cloud ไม่ใช่ทั้งสองฝั่งรวมกัน ที่สำคัญกว่านั้นคือไม่มีตัวไหนเปิดเผย
เลยว่าคะแนนความอันตรายที่ใช้จัดอันดับมาจากการคำนวณอะไร นี่คือช่องว่างที่โครงงานนี้ตั้งใจ
เติมเต็ม อธิบายต่อในหัวข้อถัดไป

ส่วนเครื่องมือภายนอกตัวเดียวที่โครงงานนี้นำมาใช้จริงคือ Cartography เครื่องมือ
โอเพนซอร์สที่ดึงข้อมูลโครงสร้างพื้นฐานคลาวด์เข้า Neo4j ให้อัตโนมัติ นำมาใช้เป็นตัวเก็บข้อมูล
ฝั่งคลาวด์ของ lab จริง (หัวข้อ~\ref{sec:impl-lab}) โดยไม่เขียนตัวเก็บข้อมูลขึ้นใหม่เองเลย
ตามที่ประกาศไว้ในขอบเขตของโครงงาน

\subsection{ช่องว่างที่โครงงานนี้เติมเต็ม}\label{sec:theory-gap}

สรุปจากงานวิจัยและเครื่องมือทั้งหมดข้างต้น โครงงานนี้ไม่ได้เสนอวิธีสร้างหรือวิเคราะห์
attack graph แบบใหม่ แต่เติมช่องว่างสามจุดที่ไม่มีงานไหนตอบพร้อมกันทั้งหมด จุดแรกคือ
วิธีให้น้ำหนัก edge ที่อธิบายที่มาได้ทุกเส้น แยกวิธีคำนวณตามชนิดของ edge: ถ้ามี CVE จริง
ใช้ EPSS~\cite{jacobs2019,epss} ตรง ๆ ถ้าเป็น misconfiguration ที่ไม่มี CVE ใช้ค่าที่
fit มาจากเวกเตอร์ CVSS~\cite{cvss31} แล้วอ้างอิง CWE และ CIS Benchmark กำกับไว้เป็น
หลักฐานประกอบทุกคลาส CWE ย่อมาจาก Common Weakness Enumeration~\cite{cwe}
คือรายการมาตรฐานที่ MITRE จัดทำไว้สำหรับจำแนกประเภทของจุดอ่อนในซอฟต์แวร์หรือการ
ตั้งค่า แต่ละรายการมีหมายเลขกำกับ เช่น CWE-521 คือ ``รหัสผ่านที่ไม่รัดกุมพอ'' ส่วน CIS
Benchmark คือคู่มือมาตรฐานการตั้งค่าระบบให้ปลอดภัยที่จัดทำโดย Center for Internet
Security~\cite{cis} ใช้อ้างอิงว่าการตั้งค่าแบบใดถือว่าหละหลวมตามมาตรฐานอุตสาหกรรม
ไม่ใช่ดุลพินิจของผู้ทำโครงงานเอง

จุดที่สองคือการเทียบ dominator tree~\cite{lengauer1979} กับ weighted
min-cut~\cite{noel2003} บนกราฟชุดเดียวกันโดยตรง แทนที่จะเลือกใช้วิธีใดวิธีหนึ่งเพียง
อย่างเดียวตามที่งานก่อนหน้าทำ จุดที่สามคือการวัดความน่าเชื่อถือของอันดับจุดตัดอย่างเป็น
ระบบ ทั้งเมื่อรบกวนน้ำหนักและเมื่อข้อมูลขาดหาย วัดด้วย Jaccard@$k$ และ Kendall's
$\tau$ เป็นคำถามที่เครื่องมือเชิงพาณิชย์ในหัวข้อก่อนไม่เคยตอบมาก่อนเลย

\section{การออกแบบระบบ}\label{sec:design}

จากทฤษฎีในหัวข้อก่อน หัวข้อนี้อธิบายว่าโครงงานนี้นำแนวคิดเหล่านั้นมาสร้างเป็นระบบจริง
อย่างไร เริ่มจากโมเดลกราฟ (หัวข้อ~\ref{sec:design-model}) ไปจนถึงตัวชี้วัดที่ใช้อ่านผลการ
ทดลอง (หัวข้อ~\ref{sec:design-metrics})

\subsection{โมเดลกราฟการโจมตี}\label{sec:design-model}

node ของกราฟในโครงงานนี้คือคู่ \texttt{(resource, privilege)} เช่น \texttt{(h001, root)}
หมายถึง ``ผู้โจมตีถือสิทธิ์ root บนเครื่อง h001'' หรือ \texttt{(s3://bucket, read)}
หมายถึง ``ผู้โจมตีอ่านข้อมูลจาก bucket นั้นได้'' การเข้ารหัสทั้งทรัพยากรและสิทธิ์ไว้ใน node
เดียวกันแบบนี้ แทนที่จะแยกเป็นสองมิติ ทำให้สถานะของผู้โจมตีสมบูรณ์ในตัวมันเอง เวลาจะ
ตรวจว่า edge หนึ่งเส้นใช้ได้หรือไม่ ดูที่ node ต้นทางเพียงอย่างเดียวก็พอ ไม่ต้องย้อนไปดูว่า
ผู้โจมตีถือสิทธิ์อะไรมาก่อนหน้านั้นจากที่ไหน

edge หนึ่งเส้นแทนการกระทำหนึ่งครั้งของผู้โจมตี เช่น หนึ่ง exploit หรือหนึ่งการเดินเครือข่าย
ไปอีกจุดหนึ่ง edge แบ่งเป็นสามชนิดตามแหล่งที่มาของความน่าจะเป็น อธิบายละเอียดในหัวข้อ
ถัดไป (หัวข้อ~\ref{sec:design-pe}) และทุกเส้นมีคุณสมบัติ \texttt{domain} กำกับไว้ว่าอยู่
ฝั่ง \texttt{onprem}, \texttt{cloud} หรือ \texttt{cross} คือข้ามจากฝั่งหนึ่งไปอีกฝั่ง edge
ที่มี \texttt{domain="cross"} คือใจกลางของวัตถุประสงค์ข้อ 1 เพราะโครงงานนี้ตั้งใจศึกษา
เส้นทางที่ข้ามจากเครือข่ายภายในองค์กรไปคลาวด์โดยเฉพาะ ตัวตรวจสอบโครงสร้าง
(\texttt{validate\_structure}) จึงบังคับว่ากราฟแบบ hybrid ทุกใบต้องมี edge ข้ามโดเมน
อย่างน้อยหนึ่งเส้นเสมอ ไม่เช่นนั้นจะไม่ถือว่าเป็นกราฟ hybrid จริง

รูปที่~\ref{fig:schema} แสดงตัวอย่างย่อส่วนที่ประกอบขึ้นจากแนวคิดทั้งหมดข้างต้น
ผู้โจมตีเริ่มจาก \texttt{(internet, anon)} แล้วไล่เจาะ CVE จริงบนเครื่อง \texttt{h001} จน
ได้สิทธิ์ \texttt{user} (edge สีน้ำเงิน, \texttt{p\_source=epss}) จากนั้นใช้รหัสผ่าน admin
ที่ตั้งซ้ำกันทุกเครื่องยกระดับเป็น \texttt{root} (edge สีส้ม, \texttt{p\_source=fitted})
ขณะเดียวกันก็เข้าถึง S3 bucket ที่เปิดอ่านสาธารณะได้โดยตรงจากอินเทอร์เน็ตเลย (edge
สีเขียว, \texttt{p\_source=deterministic}, ไม่ต้องเจาะอะไรก่อน) แล้วอ่านกุญแจ AWS ที่
หลงเหลืออยู่บนเครื่อง \texttt{h001} เพื่อไปสวมสิทธิ์ admin บนบัญชีคลาวด์ในที่สุด สีของ
edge ที่ต่างกันในรูปนี้ไม่ได้แปลว่าอันตรายมากน้อยต่างกันแต่อย่างใด แต่บอกว่าความน่าจะ
เป็น $p(e)$ ของแต่ละเส้นมาจากคนละแหล่งข้อมูล การแยกแหล่งที่มาให้ชัดเจนแบบนี้คือสิ่งที่
วัตถุประสงค์ข้อ 2 กำหนดไว้โดยตรง

โมเดลทั้งหมดนี้อยู่ภายใต้สามสมมติฐานที่ประกาศไว้ตั้งแต่ขอบเขตของโครงงาน (หัวข้อ~
\ref{sec:intro-scope}) ได้แก่ OR-semantics (node จะไปถึงได้เมื่อมี predecessor อย่างน้อย
หนึ่งตัวไปถึง ไม่ต้องครบทุกตัวแบบ AND-node ของ MulVAL), monotonic (ผู้โจมตีไม่มีวันเสีย
สิทธิ์ที่ได้มาแล้ว) และ edge independence (ความน่าจะเป็น $p(e)$ ของแต่ละ edge เป็นอิสระ
ต่อกัน ไม่ขึ้นกับ edge อื่น) ภายใต้สมมติฐานข้อสุดท้ายนี้ ความน่าจะเป็นที่เส้นทางหนึ่งจะสำเร็จ
ทั้งเส้นคือผลคูณของ $p(e)$ ของทุก edge บนเส้นทางนั้น การแปลงแต่ละ $p(e)$ เป็น
$w(e)=-\log p(e)$ ก่อนจึงเปลี่ยนการคูณให้กลายเป็นการบวก (ต้นทุนของเส้นทางคือผลรวม
ของ $w(e)$) อัลกอริทึม Dijkstra มาตรฐานใช้ได้โดยตรง และยังรักษาความหมายไว้ถูกต้องด้วย:
edge ที่ $p$ ใกล้ 1 เกือบสำเร็จแน่ จะได้ $w$ ใกล้ 0 คือต้นทุนถูก ส่วน edge ที่ $p$ ใกล้ 0
แทบไม่สำเร็จ จะได้ $w$ สูงมาก คือต้นทุนแพง ``เส้นทางที่ถูกที่สุด'' ตามน้ำหนักนี้จึงตรงกับ
``เส้นทางที่มีโอกาสสำเร็จสูงที่สุด'' พอดี

สมมติฐานเหล่านี้มีผลตามมาที่สำคัญหนึ่งข้อ ต้องเข้าใจให้ถูกตั้งแต่ต้น: ผลลัพธ์ของ shortest
path ด้วย Dijkstra (อัลกอริทึมมาตรฐานที่หาเส้นทางต้นทุนรวมต่ำสุดจากจุดหนึ่งไปอีกจุดหนึ่ง
บนกราฟที่มีน้ำหนักบวกบน edge ทุกเส้น ไล่ขยายจาก node ที่ต้นทุนสะสมน้อยที่สุดก่อนเสมอ)
บนน้ำหนัก $w(e)=-\log p(e)$ บอกได้แค่ว่า ``ถ้าผู้โจมตีเดินตามเส้นทางที่ง่ายที่สุดเพียงเส้น
เดียว ต้นทุนจะเท่าไร'' เท่านั้น ไม่ใช่โอกาสที่ระบบทั้งระบบจะถูกเจาะจริง
($P(\text{compromise})$) ในความเป็นจริงภายใต้ OR-semantics ยังมีเส้นทางอื่นที่ไปถึง
เป้าหมายเดียวกันได้อีกหลายเส้น แต่ละเส้นก็เป็นโอกาสเพิ่มเติมให้ผู้โจมตีสำเร็จ โอกาสที่แท้จริง
จึงต้องสูงกว่าที่คำนวณจากเส้นทางเดียวเสมอ ต้องรวมทุกเส้นทางเข้าด้วยกัน ไม่ใช่ดูเฉพาะเส้น
ที่ถูกที่สุดเส้นเดียว ตัวเลขที่ได้จาก Dijkstra จึงเรียกว่า \textbf{ขอบเขตล่างของต้นทุน
ผู้โจมตี} (lower bound) พูดง่าย ๆ ก็คือต้นทุนจริงของผู้โจมตีจะไม่มีทางแพงไปกว่าตัวเลขนี้เลย
มีแต่จะเท่ากันหรือถูกกว่า เพราะเส้นทางสำรองอื่น ๆ ที่ยังไม่ได้นับ มีแต่จะทำให้ผู้โจมตีทำงาน
ง่ายขึ้น ไม่ใช่ยากขึ้น ตัวเลขนี้จึงเป็นค่าประเมินความเสี่ยงต่ำสุดที่เป็นไปได้ ไม่ใช่ค่าความเสี่ยง
จริงทั้งหมด

\subsection{ที่มาของความน่าจะเป็น $p(e)$}\label{sec:design-pe}

เมื่อ edge แต่ละเส้นต้องมีความน่าจะเป็นกำกับ คำถามต่อมาคือค่านั้นมาจากไหน และ
ทำอย่างไรจึงจะตรวจสอบย้อนกลับได้ว่าทำไมจึงเป็นค่านี้ นี่คือข้อบังคับของวัตถุประสงค์ข้อ 2
วิธีแก้ของโครงงานนี้คือให้ทุก edge มีคุณสมบัติ \texttt{p\_source} หนึ่งในสี่ค่า พร้อม
\texttt{p\_input} ที่ระบุแหล่งที่มาตรงตัวของค่า $p$ นั้น:

\begin{itemize}[leftmargin=1.6em]
\item \texttt{epss} -- ใช้กับ edge ที่มี CVE จริงผูกอยู่ นำคะแนน EPSS ของ CVE นั้นมาใช้
ตรง ๆ
\item \texttt{fitted} -- ใช้กับ edge ที่เป็น misconfiguration (ไม่มี CVE ให้ใช้) คำนวณจาก
ฟังก์ชันที่ fit ไว้ระหว่างเวกเตอร์ CVSS กับ EPSS (รายละเอียดใน
หัวข้อ~\ref{sec:design-rubric} และผลการ fit ในหัวข้อ~\ref{sec:eval-pe})
\item \texttt{deterministic} -- ใช้กับ edge เชิงโครงสร้างหรือ reachability ล้วน คือ edge
ที่มีอยู่แล้วโดยการตั้งค่าของระบบเอง ไม่ต้องอาศัยการเจาะช่องโหว่ใด ๆ เพิ่มเติม ตัวอย่างเช่น
security group (กฎไฟร์วอลล์ของ AWS) ที่เปิดรับทุก IP (\texttt{0.0.0.0/0}), เครือข่ายแบบ
flat VLAN (ทุกเครื่องอยู่วงเดียวกัน คุยกันได้โดยตรงโดยไม่มีไฟร์วอลล์กั้น), VPC peering
(การเชื่อมสองเครือข่ายคลาวด์ส่วนตัวเข้าด้วยกันให้คุยกันได้โดยตรง), forest trust (การ
ตั้งค่าไว้วางใจกันระหว่างสอง domain ของ Active Directory ทำให้ user ฝั่งหนึ่งถูกมองเห็น
และอาจใช้สิทธิ์ข้ามไปอีกฝั่งได้) และ role assume (การที่ AWS IAM role หนึ่งได้รับอนุญาต
ล่วงหน้าให้สวมสิทธิ์ของอีก role หนึ่งได้ทันทีโดยไม่ต้องยืนยันตัวตนใหม่) ทุกตัวอย่างข้างต้น
ให้ $p=1.0$ เสมอ เพราะ edge พวกนี้ตัดสินแค่ว่า \emph{edge มีอยู่หรือไม่}
ไม่ได้ตัดสินว่าเจาะสำเร็จหรือไม่ ถ้าใส่ $p<1$ ให้ edge ชนิดนี้ จะกลายเป็นการประเมินความ
เสี่ยงต่ำกว่าความเป็นจริง
\item \texttt{expert} -- ค่าสำรองที่ประกาศไว้ชัดเจนว่าใช้เมื่อใด ได้แก่กรณี CVE ไม่มีคะแนน
EPSS ในฐานข้อมูล หรือ misconfiguration class นั้นยังไม่ได้ fit (เช่นในโมเดลเปรียบเทียบ
\texttt{cvss}/\texttt{uniform}/\texttt{random} ที่ใช้ในหัวข้อ~\ref{sec:design-experiments})
ไม่ใช่ค่าเริ่มต้นที่แอบใส่โดยไม่บอก
\end{itemize}

การแบ่งเป็นสามชนิดแบบนี้ ไม่ยุบเหลือสองหรือรวมเป็นหนึ่ง เป็นการตัดสินใจที่ตั้งใจ เพราะ
edge เชิงโครงสร้างกับ edge เชิง exploit มีความหมายต่างกันโดยสิ้นเชิง ถ้าผสมสองความหมาย
นี้เข้าด้วยกัน การตีความ $w(e)=-\log p(e)$ จะผิดเพี้ยนไปทันที (รายละเอียดอยู่ในภัยต่อความ
ตรงของผลข้อ~\ref{item:threat-pscale} ในหัวข้อ~\ref{sec:eval-threats})

\subsection{Rubric ของ misconfiguration}\label{sec:design-rubric}

หัวข้อก่อนบอกว่า edge ชนิด \texttt{fitted} ต้องแปลงจากเวกเตอร์ CVSS เป็น $p(e)$ แต่ก่อน
จะแปลงได้ ต้องมีคนกำหนดก่อนว่าแต่ละ misconfiguration ควรมีเวกเตอร์ CVSS หน้าตาแบบ
ไหน นี่คือหน้าที่ของ rubric (ตารางเต็มอยู่ในภาคผนวก~\ref{app:rubric}) กำหนดเวกเตอร์ให้
misconfiguration ทั้งหมด 18 class โดยยึดกฎเดียวตลอดทั้งตาราง เรียกว่า ``ให้คะแนนเทียบ
node ต้นทาง'' กล่าวคือ ปกติ CVSS ให้คะแนนจากมุมมองผู้โจมตีที่อยู่บนอินเทอร์เน็ตและยังไม่มี
อะไรในมือเลย แต่ rubric นี้ให้แต่ละเวกเตอร์อธิบาย edge เดียว $u \to v$ โดยสมมติว่าผู้โจมตี
\emph{ยืนอยู่ที่สถานะ $u$ แล้ว} ตัวอย่างเช่น \texttt{aws-key-on-host} ได้ค่า
\texttt{AV:L/PR:L} ไม่ใช่ \texttt{AV:N/PR:N} เพราะกฎนี้บังคับว่าผู้โจมตีต้องมี shell บน
เครื่องนั้นอยู่ก่อนแล้ว จึงจะอ่านไฟล์ credential ได้

ทั้ง 18 class แบ่งออกเป็นสองกลุ่มด้วยกฎง่าย ๆ ข้อเดียว: ดูว่า impact ทั้งสามด้าน (C/I/A)
เป็น \texttt{N} ครบทุกตัวหรือไม่ ถ้าใช่ แปลว่า edge นั้นให้แค่ \emph{reachability} (แค่เดินไป
ถึง ไม่ได้ทำอะไรต่อ) ไม่ใช่ exploit จริง จึงจัดเป็น \texttt{deterministic} (มี 4 class แบบนี้)
และไม่ป้อนเข้าฟังก์ชัน fit เลย เพราะ CVE ที่เผยแพร่จริงทุกตัวมี impact อย่างน้อยหนึ่งด้านที่
ไม่ใช่ \texttt{N} เวกเตอร์แบบ all-N จึงอยู่นอกขอบเขตข้อมูลที่ฟังก์ชัน fit เคยเห็นมาก่อน
ถ้าไม่ใช่ all-N แปลว่าเป็น exploit หรือ abuse ก้าวหนึ่งจริง จัดเป็น \texttt{fitted} (มี 14
class แบบนี้) แต่ละแถวของทั้ง 18 class อ้างอิง CWE และ/หรือ CIS Benchmark ที่ตรงกับคลาส
นั้นกำกับไว้ด้วย เพื่อให้ใครก็ตามตรวจสอบย้อนกลับได้ว่าทำไมจึงกำหนดเวกเตอร์แบบนี้ ไม่ใช่
ดุลพินิจที่ไม่มีการบันทึกไว้

\subsection{ตัวสร้างกราฟจำลอง}\label{sec:design-gen}

เมื่อมีทั้งโมเดลกราฟและวิธีให้น้ำหนักแล้ว ส่วนถัดไปคือเครื่องมือที่สร้างกราฟตัวอย่างขึ้นมา
จำนวนมากสำหรับทดลอง ตัวสร้างกราฟ (\texttt{attackpath/gen.py}) รับพารามิเตอร์สี่ตัว ได้แก่
ขนาดกราฟ $n \in \{50, 200, 800\}$ node, ความหนาแน่นของ edge ข้ามโดเมน
(\texttt{low}/\texttt{med}/\texttt{high}), ระดับการแบ่งส่วนเครือข่าย
(\texttt{flat}/\texttt{3tier}/\texttt{micro}) และ seed สำหรับสุ่ม

เมื่อสร้างกราฟ node ประมาณ 60\% จะอยู่ฝั่ง on-prem และ 40\% อยู่ฝั่ง cloud ฝั่ง on-prem
แต่ละเครื่องมีสอง node เสมอคือ \texttt{user} และ \texttt{root} เชื่อมกันด้วย edge ชนิด
\texttt{cve} จริง สุ่มเลือกจาก pool ของ CVE ที่มีทั้ง vector และ EPSS พร้อมกันในข้อมูลที่ดึง
มา อธิบายไว้ในหัวข้อ~\ref{sec:impl-pipeline} ส่วน edge ที่เดินเครือข่ายระหว่างเครื่อง
(lateral movement) แบ่งสัดส่วนประมาณ 50\% เป็น \texttt{cve}, 30\% เป็น
\texttt{misconfig} และ 20\% เป็น \texttt{deterministic} จำนวน edge ที่แต่ละเครื่องเชื่อม
ออกไปได้ (degree) ถูกกำหนดตามระดับการแบ่งส่วนโดยตรง คือ \texttt{micro}=1 น้อยกว่า
\texttt{3tier}=2 น้อยกว่า \texttt{flat}=3 เป็นการออกแบบไว้ตั้งแต่ต้น ไม่ใช่ผลพลอยได้จาก
การสุ่ม

ส่วน edge ที่ข้ามโดเมนสุ่มมาจากคลาสที่กำหนดไว้ล่วงหน้า 5 ชนิด (เช่น
\texttt{aws-key-on-host}, \texttt{ssrf-imdsv1-token}) จำนวนเส้นที่สุ่มได้ขึ้นกับความ
หนาแน่นที่ตั้งไว้และขนาดกราฟ หลังจากสร้างโครงสร้างหลักเสร็จแล้ว อาจมีบางคู่ (entry,
target) ที่ยังไปไม่ถึงกัน ตัวซ่อมกราฟ (\texttt{\_repair}) จึงเติม edge ที่ถูกต้องตามนโยบาย
เท่าที่จำเป็นเข้าไป ไม่ใช่ edge สมมติที่แต่งขึ้นมาลอย ๆ เพื่อให้ทุกคู่ไปถึงกันได้แน่นอน การ
แบ่งส่วนแบบ \texttt{micro} ซึ่งเข้มงวดกว่าแบบอื่น มักต้องซ่อมมากกว่า นี่คือที่มาของ
ข้อสังเกตในหัวข้อ~\ref{sec:eval-cross} ที่ว่าสัดส่วน ``ต้องข้ามโดเมน'' ที่วัดได้ส่วนหนึ่งมาจาก
การซ่อมกราฟ ไม่ใช่โครงสร้างธรรมชาติล้วน ๆ

นอกจากนี้จำนวน entry และ target ยังถูกล็อกไว้ตายตัวตามขนาดกราฟ ($n{=}50$ ให้ 3
entry กับ 2 target, $200$ ให้ $5/3$, $800$ ให้ $8/4$) เพราะการคำนวณ
\texttt{pairwise\_dominators} มีต้นทุนที่โตตามจำนวน entry คูณจำนวน target ถ้าไม่ล็อกไว้
ต้นทุนนี้อาจหลุดจากที่ควบคุมได้ง่าย ตารางปัจจัยทั้งหมด (ขนาด $\times$ ความหนาแน่น $\times$
การแบ่งส่วน) มี 27 เซลล์ แต่ละเซลล์สร้างกราฟซ้ำ 8 ครั้ง (\texttt{rep}) รวมเป็น 216
โครงสร้าง เกินขั้นต่ำ 200 กราฟตามข้อเสนอแม้นับเฉพาะโครงสร้างก่อนคูณด้วยโมเดลน้ำหนัก
seed ของแต่ละโครงสร้างคำนวณจากตำแหน่งของเซลล์และ \texttt{rep} โดยตรง ไม่ขึ้นกับว่าครั้ง
นั้นเรียกใช้กี่ขนาดหรือกี่ \texttt{rep} ทำให้กราฟชุดย่อยใด ๆ ทำซ้ำได้เหมือนเดิมเสมอ (ตรวจสอบ
จริงแล้วด้วยการรันข้าม \texttt{PYTHONHASHSEED} หลายค่า) และทุกกราฟยังบันทึก
\texttt{cve\_pool\_size} กับ \texttt{epss\_snapshot} กำกับไว้ด้วย เพื่อให้เห็นชัดว่าการทำซ้ำ
นี้อ้างอิงข้อมูล snapshot ชุดไหน

\subsection{นิยามจุดตัด}\label{sec:design-chokepoint}

เมื่อมีกราฟพร้อมน้ำหนักแล้ว คำถามหลักของโครงงานนี้คือ ``จุดตัด'' (choke point) อยู่ตรง
ไหน แต่คำว่าจุดตัดเองมีได้หลายความหมาย โครงงานนี้จึงแยกไว้ชัดเจนเป็นสามนิยาม
(รายละเอียดเชิงตัวเลขของแต่ละนิยามอยู่ในหัวข้อ~\ref{sec:eval-cut-defs}):

\begin{itemize}[leftmargin=1.6em]
\item \textbf{global} -- node ที่อยู่บนทุกเส้นทางของ\emph{ทุกคู่} (entry, target) เป็นนิยาม
ที่เข้มที่สุด
\item \textbf{per-target} -- node ที่อยู่บนทุกเส้นทางที่ไปถึง target หนึ่งตัว ไม่ว่าจะมาจาก
entry ตัวไหน
\item \textbf{per-pair} -- node ที่อยู่บนทุกเส้นทางของคู่ (entry, target) หนึ่งคู่โดยเฉพาะ
เป็นนิยามที่หลวมที่สุดและให้เซตใหญ่ที่สุด
\end{itemize}

นิยาม global คำนวณได้สองวิธีที่พิสูจน์ได้ว่าให้ผลเท่ากันเสมอ วิธีแรกเติม super-source
เข้าไปทุก entry และ super-sink ออกจากทุก target แล้วใช้ dominator tree มาตรฐาน
(ผ่าน \texttt{nx.immediate\_dominators}) วิธีที่สองคำนวณทีละคู่ (entry, target) แล้วนำ
ผลมาตัดฉันทามติ (intersect) กัน เนื่องจากสองวิธีนี้พิสูจน์แล้วว่าเท่ากันเสมอ การรายงาน
``อัตราความไม่ตรงกัน'' ระหว่างสองวิธีนี้จึงไม่ใช่ผลการทดลอง แต่เป็นเพียงแบบทดสอบความ
ถูกต้องของโค้ดเท่านั้น ถ้าตัวเลขไม่ตรงกันจริง แปลว่าโค้ดมีบั๊ก ไม่ใช่ข้อค้นพบ อีกจุดที่ต้อง
ระวังคือคู่ (entry, target) ที่ target ไปไม่ถึงเลยต้อง\emph{ข้าม}ไป ไม่นับเป็นเซตว่าง เพราะ
ถ้านับเป็นเซตว่าง ความเท่ากันของสองวิธีข้างต้นจะพังทันที เซตว่างตัดกับเซตอะไรก็ได้เซตว่าง
เสมอ ซึ่งไม่ใช่สิ่งที่ต้องการวัด

สามนิยามข้างต้นบอกได้แค่ว่า node อยู่ในเซตจุดตัดหรือไม่ แต่ยังจัดอันดับ node ไม่ได้ว่าตัว
ไหนสำคัญกว่าตัวไหน เพื่อให้จัดอันดับได้ โครงงานนี้จึงให้คะแนนแต่ละ node ด้วยสูตร
$\Delta(v) = \text{cost}(G{-}v) - \text{cost}(G)$ คือต้นทุนรวมของผู้โจมตีที่เพิ่มขึ้นเมื่อลบ
node $v$ ทิ้งไปจากกราฟ (ต้นทุนรวมของผู้โจมตีในที่นี้คือผลรวมต้นทุนของเส้นทางถูกที่สุด
ของทุกคู่ที่ยังไปถึงกันได้) ข้อค้นพบที่สำคัญคือ global dominator set พิสูจน์ได้ว่าเท่ากับเซต
$\{v : \Delta(v) = \infty\}$ พอดี (ตรวจสอบจริงด้วย brute force ในหัวข้อ~
\ref{sec:impl-repro}) พูดอีกแบบคือ จุดตัดเชิงโครงสร้างไม่ใช่วิธีที่แยกต่างหากจากคะแนนเชิง
ความน่าจะเป็นเลย แต่เป็นกรณีสุดขั้วของมันเอง กรณีที่ต้นทุนเพิ่มขึ้นจนเป็นอนันต์

โค้ดจริงที่คำนวณ $\Delta(v)$ อยู่ในฟังก์ชัน \texttt{delta\_cost\_scores} ของไฟล์
\texttt{attackpath/chokepoints.py} ทำตามนิยามนี้ตรงตัวมาก: ลบ node ออกทีละตัว
คำนวณต้นทุนรวมใหม่ แล้วลบกับต้นทุนเดิม

\begin{quote}\small\begin{verbatim}
for v in candidates:
    H = G.copy()
    H.remove_node(v)
    after = _pair_costs(H, entries, targets, weight)
    for pair, c in base.items():
        if pair in after:
            delta += after[pair] - c
        else:
            cut_n += 1
\end{verbatim}\end{quote}

สังเกตบรรทัดสุดท้าย: ถ้าลบ \texttt{v} แล้วคู่ \texttt{(entry, target)} หนึ่งคู่หายไปจาก
\texttt{after} (คือไปถึงกันไม่ได้อีกเลย) โค้ดจะนับเป็น \texttt{cut\_n} แทนที่จะพยายามคำนวณ
\texttt{after[pair] - c} ซึ่งจะเป็นการลบด้วยอนันต์ที่ไม่มีความหมาย \texttt{cut\_n} ที่มากกว่า
ศูนย์จึงเทียบเท่ากับ $\Delta(v)=\infty$ ในนิยามทางคณิตศาสตร์พอดี และเป็นเหตุผลที่ฟังก์ชันนี้
คืนค่าเป็นคู่ \texttt{(cut\_n, delta, blocked)} แทนที่จะคืนตัวเลขเดียว เพื่อให้แยกกรณี
``ตัดได้ทั้งคู่'' ออกจากกรณี ``ทำให้แพงขึ้น'' ได้เสมอ ไม่ปนกัน

ข้อควรระวังอีกจุดคือ node ทุกตัวในกลุ่ม $\Delta=\infty$ นี้มีค่าเท่ากันหมด เพราะลบตัวไหน
ก็ตัดทุกเส้นทางเหมือนกัน จึงจัดอันดับกันเองภายในกลุ่มไม่ได้เลย ด้วยเหตุนี้ทุกครั้งที่รายงาน
อันดับจึงต้องกำกับด้วย $n_{\inf} = |\{v : \Delta(v)=\infty\}|$ (จำนวน node ในกลุ่มนี้)
เพราะถ้า $n_{\inf} \geq k$ การเลือก top-$k$ จากกลุ่มนี้จะเป็นการเลือกโดยพลการ และค่า
Jaccard@$k$ ที่คำนวณได้จะไม่มีความหมายอีกต่อไป ต้องรายงานสัดส่วนกราฟที่เข้าเงื่อนไขนี้
คู่กับ Jaccard@$k$ เสมอ เช่นเดียวกับ $n_{\text{tie\_at\_}k}$ ที่นับว่า node กี่ตัวมีคะแนน
เสมอกับ node อันดับที่ $k$ พอดี (เมื่อคะแนนเท่ากัน จะตัดสินด้วยเลข id แทน เพื่อให้อันดับทำ
ซ้ำได้เสมอ)

\subsection{Weighted Min-Cut}\label{sec:design-mincut}

ตามที่กล่าวไว้ในหัวข้อ~\ref{sec:theory-hardening} โครงงานนี้ต้องการเทียบ dominator กับ
weighted min-cut (วัตถุประสงค์ข้อ 3) แต่ปัญหาคือทั้งสองวิธีคืนค่าคนละหน่วยกัน: dominator
คืนเซตของ node ส่วน min-cut แบบมาตรฐานคืนเซตของ edge ที่ถูกตัด จะเทียบกันตรง ๆ ไม่ได้
ทางแก้คือเทคนิคที่เรียกว่า node-splitting: แตก node $v$ ทุกตัวออกเป็นสองส่วนคือ
$v_{\text{in}}$ กับ $v_{\text{out}}$ แล้ววางน้ำหนักของ $v$ ไว้บน edge ภายในที่เชื่อมสองส่วน
นี้เข้าด้วยกัน ส่วน edge เดิมของกราฟให้ capacity เป็นอนันต์ทั้งหมด เมื่อรัน min-cut
มาตรฐาน (\texttt{nx.minimum\_cut}) บนกราฟที่แตกแล้วนี้ cut ที่ได้จะเลือกตัด edge
ภายในเท่านั้น เพราะไม่มีทางถูกกว่าตัด edge เดิมที่ capacity อนันต์เลย ผลลัพธ์จึงแปลงกลับ
เป็นเซตของ node ได้ตรง ๆ นอกจากนี้ entry และ target เองก็ถูกกำหนดให้มี capacity
อนันต์เสมอด้วย เพราะการ ``ป้องกัน'' ระบบด้วยการลบจุดเริ่มต้นหรือเป้าหมายทิ้งไปเลยนั้น
ไม่ใช่แนวทางป้องกันที่สมเหตุสมผลตั้งแต่แรก

โค้ดส่วนที่ทำหน้าที่แตก node และกำหนด capacity ตามที่อธิบายข้างต้น อยู่ในฟังก์ชัน
\texttt{node\_min\_cut} ของไฟล์ \texttt{attackpath/chokepoints.py}
ใจความสำคัญคือสามบรรทัดนี้:

\begin{quote}\small\begin{verbatim}
for v in G.nodes:
    c = INF if v in protected else float(cap(G, v))
    S.add_edge((v, "in"), (v, "out"), capacity=c)
for u, v in G.edges:
    S.add_edge((u, "out"), (v, "in"), capacity=INF)
\end{verbatim}\end{quote}

บรรทัดแรกคือหัวใจของ node-splitting: สร้าง edge ภายในจาก \texttt{(v, "in")} ไป
\texttt{(v, "out")} โดยให้ capacity เท่ากับน้ำหนักของ node นั้น ยกเว้นถ้า \texttt{v} เป็น
entry/target (\texttt{protected}) จะให้ \texttt{INF} แทน (ตัดไม่ได้) บรรทัดที่สองคือการเติม
edge เดิมของกราฟกลับเข้าไป แต่บังคับให้ capacity เป็น \texttt{INF} เสมอ เพื่อไม่ให้
\texttt{nx.minimum\_cut} มีทางเลือกตัด edge เดิมได้เลย มันจึงถูกบีบให้ตัดได้เฉพาะ edge
ภายในที่เพิ่งสร้างขึ้น ซึ่งแปลงกลับเป็นเซตของ node ได้ตรง ๆ ตามที่อธิบายไว้ข้างต้น

โครงงานนี้รายงานผลของ capacity สามแบบคู่กันเสมอ เพราะแต่ละแบบตอบคำถามต่างกัน
แบบแรกคือ \texttt{unit} (นับ 1 ต่อ node ไม่สนน้ำหนักเลย) ซึ่งเทียบหน่วยตรงกับ dominator
ได้โดยตรง เพราะ dominator เองก็ไม่อ่านน้ำหนักเช่นกัน แบบที่สองคือ \texttt{prob} (ใช้ค่า
$p$ สูงสุดของ edge ขาเข้า) เป็นค่าตั้งต้นที่ใช้จริง และแบบที่สามคือ \texttt{cost} (ใช้ $-\log p$
ของ edge ขาเข้าที่ถูกที่สุด) capacity แบบ \texttt{cost} นี้มีปัญหา: บนกราฟที่มี edge เชิง
โครงสร้าง ($p=1$ จึง $w=0$) node ที่เข้าถึงได้ฟรีจะมี capacity เป็นศูนย์ ทำให้ min-cut ยุบ
ไปเลือกเซต capacity ศูนย์ที่เลือกได้โดยพลการ เพราะตัดตรงไหนก็ต้นทุนเท่ากันคือศูนย์ วัด
ได้จริงในหัวข้อ~\ref{sec:eval-cut-agree} เพราะเหตุนี้ \texttt{cost} จึงรายงานไว้เป็นเพียง
คอลัมน์ sensitivity เสริม ไม่ใช่ค่าหลักของการเปรียบเทียบ

\subsection{ตัวชี้วัด}\label{sec:design-metrics}

สุดท้ายคือคำถามว่าจะอ่านผลการทดลองด้วยตัวเลขอะไร ตัวชี้วัดหลักที่ใช้ตลอดทั้งรายงานคือ
\textbf{Jaccard@$k$} ($k=5,10$) เทียบว่า node ที่ติดอันดับ top-$k$ ก่อนและหลังการรบกวน
(เช่น รบกวนน้ำหนักหรือลบ edge ออก) ทับซ้อนกันมากน้อยแค่ไหน คิดจากสูตรง่าย ๆ คือขนาด
ของเซตที่ node ทั้งสองชุดมีร่วมกัน หารด้วยขนาดของเซตรวมทั้งสองชุด ค่า 1.0 แปลว่า
top-$k$ เหมือนเดิมทุกตัว ส่วน 0 แปลว่าไม่เหลือ node ร่วมกันเลย ตัวอย่างเช่น ถ้า top-5
ก่อนรบกวนคือ $\{A,B,C,D,E\}$ และหลังรบกวนกลายเป็น $\{A,B,C,D,F\}$ (มี $F$ เข้ามา
แทน $E$) เซตร่วมมี 4 ตัว $(A,B,C,D)$ ส่วนเซตรวมมี 6 ตัว $(A,B,C,D,E,F)$ Jaccard@5
จึงเท่ากับ $4/6 \approx 0.667$

ตัวชี้วัดรองคือ Kendall's $\tau$ วัดว่าลำดับคู่ node สองตัวสลับที่กันหรือไม่เมื่อเทียบก่อน--หลัง
คิดเป็นสัดส่วนของคู่ที่ลำดับคงเดิมลบด้วยคู่ที่ลำดับสลับ ค่าอยู่ระหว่าง $-1$ ถึง $1$ เป็นตัวชี้วัด
รองเพราะเมื่อคำนวณบนทั้งกราฟ มักถูก tie จำนวนมากกลบ node ส่วนใหญ่ที่ไม่อยู่บนเส้นทาง
ถูกสุดเลยจะมีคะแนนเท่ากันหมดคือศูนย์ ทำให้ $\tau$ วัดอะไรไม่ค่อยได้ ตัวชี้วัดทั้งสองคำนวณ
จากคะแนน $\Delta(v)$ ที่นิยามไว้ในหัวข้อ~\ref{sec:design-chokepoint} เท่านั้น

นอกจากตัวชี้วัดด้านอันดับจุดตัดสองตัวข้างต้น หัวข้อ~\ref{sec:eval-pe} ที่ประเมินความแม่น
ของฟังก์ชันแปลง CVSS$\to$EPSS ยังใช้ Spearman's $\rho$ กำกับคู่กับ $R^2$ เสมอ
$\rho$ คือสัมประสิทธิ์สหสัมพันธ์แบบอันดับ (rank correlation) แทนที่จะเทียบค่าตัวเลขจริง
แบบที่ $R^2$ ทำ มันแปลงข้อมูลทั้งสองชุดเป็น\emph{อันดับ}ก่อน แล้ววัดว่าอันดับของสองชุด
สอดคล้องกันแค่ไหน ค่าเข้าใกล้ 1 แปลว่าเรียงลำดับตรงกันเกือบสมบูรณ์ รายงานคู่กับ $R^2$
เสมอเพราะ $R^2$ ไวต่อค่าตัวเลขที่คลาดเคลื่อนไปมาก (เช่นทำนายผิดสิบเท่า) แต่ $\rho$
สนใจแค่ว่าอันดับถูกหรือไม่ ซึ่งตรงกับสิ่งที่โครงงานนี้ต้องการจริง ๆ คือการจัดอันดับจุดตัด ไม่ใช่
การทำนายค่าตัวเลขให้แม่น

Jaccard@$k$ ยังมีสองรูปแบบที่รายงานคู่กันเสมอ แบบแรกคือแบบปกติ (ตัด top-$k$ ตรง ๆ
ตามลำดับ) แบบที่สองนับ node ที่คะแนนเสมอกับ node อันดับที่ $k$ เข้าไปด้วย
(\texttt{top\_k\_set}) ต้องมีแบบที่สองเพราะโครงสร้างแบบโซ่ของกราฟทำให้ node ที่ติดกัน
หลายตัวมีคะแนนเท่ากันเป๊ะได้บ่อย ถ้าใช้ plain top-$k$ อย่างเดียว การตัดกลุ่มที่คะแนน
เท่ากันตามเลข id จะให้ค่า Jaccard สูงเกินจริง เพราะวิธีตัดสินใจ (tie-break) เหมือนกันทุก
ครั้งอยู่แล้ว

ในการรายงานตัวเลขทั้งหมด ค่าเฉลี่ยทุกตัวคำนวณบน\emph{กราฟ} ไม่ใช่บนแถวของผลลัพธ์
เพราะแต่ละกราฟมีการทำซ้ำ (\texttt{rep}) ของสัญญาณรบกวนหลายครั้ง แถวพวกนั้นไม่เป็น
อิสระต่อกัน มาจากกราฟเดียวกัน ถ้านับทุกแถวเท่ากันจะประเมินความแม่นยำสูงเกินจริง ช่วง
ความเชื่อมั่น 95\% ของค่าเฉลี่ยจึงคำนวณด้วยวิธี bootstrap แบบสุ่มเลือก\emph{กราฟ}ซ้ำได้
(resample with replacement) ไม่ใช่สุ่มเลือกแถว ส่วนสัดส่วนของกราฟที่มีคุณสมบัติหนึ่ง ๆ
(เช่น ``มี global choke point'') ใช้ช่วงความเชื่อมั่นแบบ Wilson แทน เพราะจำนวนกราฟที่
เข้าเงื่อนไขแบบนี้มักมีน้อย ทำให้สูตรปกติ (normal approximation) ให้ช่วงที่ผิดสัดส่วนได้ง่าย
