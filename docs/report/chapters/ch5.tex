\chapter{ประเมินผล อภิปราย และวิเคราะห์}\label{ch:eval}

บทนี้รายงานผลการทดลองทั้งเจ็ดชุดที่วางแผนไว้ในหัวข้อ~\ref{sec:design-experiments} เรียง
ตามวัตถุประสงค์ของข้อเสนอโครงงาน เริ่มจากความแม่นของการให้น้ำหนัก (วัตถุประสงค์ข้อ 2)
ไปจนถึงผลจาก lab จริง (วัตถุประสงค์ข้อ 5) แล้วปิดท้ายด้วยการอภิปรายว่าผลเหล่านี้มีจุดอ่อน
ตรงไหนบ้าง (หัวข้อ~\ref{sec:eval-threats} และ~\ref{sec:eval-limits}) ตัวเลขทุกตัวในบทนี้
คำนวณจากไฟล์ผลลัพธ์ดิบใน \texttt{results/*.csv} ที่เกิดจากการรัน \texttt{experiments/run.py}
บนกริด 216 โครงสร้าง $\times$ 4 โมเดลน้ำหนัก (รวม 864 กราฟถ่วงน้ำหนัก) แล้วสรุปเป็น
ตารางด้วย \texttt{experiments/analyze.py} (ขั้นตอนทำซ้ำเต็มอยู่ในภาคผนวก~\ref{app:reproduce})
และทุกครั้งที่แก้ตัวเลขในบทนี้ จะตรวจสอบย้อนกลับด้วย \texttt{scripts/check\_claims.py}
ว่ายังตรงกับไฟล์ผลลัพธ์จริงเสมอ ไม่ใช่ตัวเลขที่พิมพ์ลอย ๆ โดยไม่มีไฟล์รองรับ

\section{ผลการประมาณค่า $p(e)$ จาก CVSS (วัตถุประสงค์ข้อ 2)}\label{sec:eval-pe}

ในหัวข้อ~\ref{sec:design-pe} อธิบายไว้ว่า edge ที่เป็น misconfiguration ไม่มี CVE ผูกอยู่
จึงไม่มีคะแนน EPSS ให้ใช้โดยตรง ทางแก้ของโครงงานนี้คือกำหนดเวกเตอร์ CVSS ให้แต่ละ
คลาสของ misconfiguration ตาม rubric (ภาคผนวก~\ref{app:rubric}) แล้วใช้ฟังก์ชันที่
เรียนรู้ความสัมพันธ์ระหว่างเวกเตอร์ CVSS กับคะแนน EPSS ของ CVE จริง แปลงเวกเตอร์นั้น
เป็นค่าความน่าจะเป็น $p(e)$ หัวข้อนี้ตอบคำถามว่าฟังก์ชันที่แปลงให้นั้นแม่นยำแค่ไหน ซึ่ง
สำคัญเพราะความคลาดเคลื่อนของ $p(e)$ ส่งผลต่ออันดับเส้นทางโดยตรง

\subsection{ข้อมูลและวิธีการ}\label{sec:eval-pe-data}

ข้อมูลที่ใช้ฝึกฟังก์ชันนี้คือ CVE จำนวน 46{,}360 รายการ ที่มีทั้งเวกเตอร์ CVSS และคะแนน
EPSS ครบทั้งคู่ เวกเตอร์ CVSS ดึงมาจาก NVD (National Vulnerability Database ฐานข้อมูล
ช่องโหว่กลางของสหรัฐฯ) ผ่าน API เวอร์ชัน 2.0 เป็นบล็อกละ 2{,}000 รายการ รวม 33 หน้า
ด้วยสคริปต์ \texttt{scripts/pull\_data.py} ตามที่อธิบายไว้ในหัวข้อ~\ref{sec:impl-pipeline}
ส่วนคะแนน EPSS มาจาก snapshot วันที่ 2026-08-26 ไฟล์ดิบดาวน์โหลดจาก
\texttt{epss.empiricalsecurity.com} เว็บทางการที่ FIRST.org เผยแพร่คะแนน EPSS
รายวัน เป็น CVE ที่เผยแพร่ระหว่าง 2017-03-20 ถึง 2026-08-06 การสุ่มทุกขั้นตอนใช้ seed
เดียวกันคือ 20260826
เพื่อให้ทำซ้ำได้ ตัวแปรตามที่ใช้ฝึกคือ EPSS ในสเกล logit คือ $\log\frac{p}{1-p}$
(แปลงความน่าจะเป็นที่ปกติอยู่ในช่วง 0--1 ให้กระจายไปทั่วเส้นจำนวนจริง แทนที่จะกระจุก
ตัวอยู่ใกล้ 0 อย่างที่ค่า EPSS ส่วนใหญ่เป็นจริง) ไม่ใช่สเกลความน่าจะเป็นตรง ๆ เหตุผลที่
เลือกฝึกในสเกลนี้คือค่าความน่าจะเป็นดิบของ EPSS เบ้ไปทางค่าน้อยมาก (ส่วนใหญ่ต่ำกว่า
1\%) การถดถอยเชิงเส้นตรง ๆ บนสเกลดิบจะให้น้ำหนักกับ CVE ที่หายากแต่ค่าสูงน้อยเกินไป
และเปรียบเทียบฟังก์ชัน 4 แบบด้วยกัน ได้แก่ ค่าเฉลี่ยคงที่ (constant baseline) เป็นเกณฑ์ขั้น
ต่ำ, การถดถอยเชิงเส้นจากคะแนนฐาน CVSS เพียงตัวเดียว, การถดถอยเชิงเส้นจาก 8 metric
ของ CVSS เรียกย่อว่า OLS (Ordinary Least Squares) ชื่อเรียกการถดถอยเชิงเส้นแบบ
``กำลังสองน้อยที่สุด'' ในหมู่งานสถิติ หมายถึงวิธีหาสัมประสิทธิ์ที่ทำให้ผลรวมของค่าคลาดเคลื่อน
ยกกำลังสองน้อยที่สุด เป็นวิธีถดถอยเชิงเส้นมาตรฐานที่สุด และสุดท้ายคือ gradient boosting
จาก 8 metric เดียวกัน เรียกย่อว่า GBM โมเดลนี้คือ ensemble ของ decision tree หลายร้อยต้น
ที่เรียนแก้ไขความผิดพลาดของกันและกันทีละขั้น ให้ความแม่นสูงกว่า OLS ได้ แต่ไม่สามารถ
อ่านได้ว่าแต่ละตัวแปรมีผลต่อผลลัพธ์อย่างไร ต่างจาก OLS ที่บวกสัมประสิทธิ์ทีละตัวแปรตรง ๆ
ตัวชี้วัด
ความแม่นในตารางที่~\ref{tab:fit} คำนวณบนข้อมูลทดสอบ 25\% (สุ่มแบ่งจาก CVE ทั้ง
46{,}360 รายการ ด้วย seed เดียวกันคือ 20260826) ที่กันไว้ไม่ให้ฟังก์ชันเห็นตอนฝึก

\subsection{ผลการ fit}\label{sec:eval-pe-fit}

ตัวเลขหลักที่ใช้อ่านตารางถัดไปคือ $R^2$ (สัมประสิทธิ์การตัดสินใจ) ซึ่งตอบคำถามว่า
``โมเดลอธิบายความแปรปรวนของข้อมูลจริงได้กี่เปอร์เซ็นต์'' ค่า 1.0 แปลว่าทำนายตรงเป๊ะทุก
จุด ค่า 0 แปลว่าทำนายได้พอ ๆ กับการทายค่าเฉลี่ยคงที่ลอย ๆ และค่าติดลบแปลว่าแย่กว่า
การทายค่าเฉลี่ยเสียอีก ตารางรายงาน $R^2$ สามสเกลต่างกัน (logit, prob, top 10\%) เพราะ
ตัวเลขเดียวกันให้ความรู้สึกต่างกันมากตามสเกลที่วัด ดังจะเห็นในสามข้อถัดไป

ตารางที่~\ref{tab:fit} บอกสามเรื่องที่ต้องอ่านด้วยกัน

\begin{enumerate}[leftmargin=1.6em]
\item \textbf{โมเดลที่ใช้ตั้งราคา edge จริงคือ OLS จาก 8 metric ไม่ใช่ตัวที่ได้คะแนนสูงสุด}
GBM ให้ค่าสูงกว่าเล็กน้อย แต่เป็นกล่องดำที่อธิบายไม่ได้ว่าทำไมจึงให้ค่านี้ ขณะที่ OLS บวก
สัมประสิทธิ์แต่ละตัวกันในสเกล logit ตรวจสอบย้อนกลับได้ทีละ metric ซึ่งตรงกับวัตถุประสงค์
ข้อ 2 ที่ว่า $p(e)$ ต้องอธิบายที่มาได้ ตัวเลขทั้งหมดที่รายงานต่อจากนี้จึงเป็นของ OLS เสมอ
\item \textbf{ในหน่วยที่ใช้งานจริง ฟังก์ชันนี้ไม่ดีกว่าการทายค่าเฉลี่ยเลย} $R^2$ ใน
สเกลความน่าจะเป็น (คอลัมน์ ``prob'') ติดลบทุกโมเดล รวมถึง OLS ด้วย ค่า 0.219 ที่ดูเหมือน
พอใช้ได้จึงเป็นเพียงตัวเลขในสเกล logit เท่านั้น ซึ่งอธิบายความแปรปรวนได้ประมาณหนึ่งใน
ห้าของข้อมูล
\item \textbf{ความคลาดเคลื่อนไม่ได้กระจายสม่ำเสมอ แต่กระจุกอยู่ที่ EPSS สูง} ฟังก์ชันที่ fit
ได้ทำนายค่าสูงสุดเพียง 0.0186 ขณะที่ EPSS จริงสูงสุดถึง 0.99999 พูดง่าย ๆ คือฟังก์ชันนี้
``ไปไม่ถึงหาง'' ของการแจกแจง จึงถดถอยเข้าหาค่าฐาน (base rate) ที่ประมาณ 0.0055 แทน
\end{enumerate}

รูปที่~\ref{fig:fitscatter} แสดงข้อสามข้างต้นให้เห็นเป็นภาพ: แกนนอนคือ EPSS จริง แกนตั้ง
คือค่าที่ฟังก์ชัน fit ทำนาย (ทั้งสองแกนเป็น log scale) ถ้าฟังก์ชันทำนายแม่น จุดทั้งหมดควร
เกาะอยู่บนเส้นประทแยงมุม (y=x) แต่สิ่งที่เห็นจริงคือจุดสีแดง (CVE ที่มี EPSS สูงสุด 10\%)
แทบทั้งหมดอยู่\emph{ใต้}เส้นทแยงมุมมาก และค่าที่ทำนายได้ไม่เคยพุ่งขึ้นไปเกินแนวนอนแคบ ๆ
แถวประมาณ 0.01--0.02 เลย ไม่ว่า EPSS จริงจะสูงแค่ไหนก็ตาม ภาพนี้คือ ``ฟังก์ชันไปไม่
ถึงหาง'' ที่กล่าวไว้ข้างต้น เห็นเป็นรูปธรรมชัดเจน ไม่ใช่แค่ตัวเลขลอย ๆ

อีกจุดที่ต้องระวังคือค่า $R^2 = 0.219$ ในตารางที่~\ref{tab:fit} มาจากการแบ่งข้อมูลทดสอบ
แบบสุ่มราย CVE ซึ่งมองโลกในแง่ดีกว่าการใช้งานจริงเล็กน้อย เพราะ CVE ที่คล้ายกันมากอาจ
ตกอยู่คนละฝั่งของการแบ่ง ทำให้ฟังก์ชัน ``จำ'' รูปแบบที่เห็นจากฝั่งฝึกได้บางส่วน เพื่อตรวจสอบ
เรื่องนี้ จึงลองแบ่งข้อมูลแบบที่เข้มงวดขึ้น: เมื่อกันทั้งหน้า NVD ออกจากกันแทนที่จะสุ่มราย CVE
$R^2$ ลดเหลือ 0.156 และเมื่อกันทั้งปีออกจากกัน $R^2$ ลดเหลือ 0.150 กรณีที่เข้มที่สุดคือฝึก
ด้วย CVE ถึงปี 2022 เท่านั้น แล้วทดสอบกับ CVE ตั้งแต่ปี 2023 เป็นต้นไป กรณีนี้ $R^2$
ติดลบไปเลย ($-0.863$) แต่ที่น่าสนใจคือ Spearman $\rho$ ยังอยู่ที่ 0.542 แทบไม่ตก ผล
นี้แปลว่า \emph{ระดับ} ของค่า $p(e)$ ที่ทำนายได้เลื่อนไปตามเวลา (ทำนายแม่นน้อยลงถ้าดู
ค่าสัมบูรณ์) แต่ \emph{อันดับ} ระหว่าง CVE ยังรักษาไว้ได้ (ตรวจสอบจริงด้วย
\texttt{scripts/audit\_data.py}) ข้อสรุปเชิงปฏิบัติคือ ไม่ควรอ้างว่าฟังก์ชันนี้ทำนายค่า EPSS
ของ CVE ใหม่ได้แม่น ใช้ได้เพียงเพื่อจัดอันดับเท่านั้น

\subsection{ความคลาดเคลื่อนในหน่วย log}\label{sec:eval-pe-logerr}

ผลข้างต้นชวนให้ถามต่อว่า ความคลาดเคลื่อนขนาดนี้กระทบ \emph{อันดับเส้นทาง} มากแค่ไหน
จริง ๆ เพราะต้นทุนของเส้นทางคือผลรวมของ $-\log p$ บน edge ตลอดเส้นทางนั้น ตัวเลขที่
บอกว่าอันดับเส้นทางจะเปลี่ยนหรือไม่จึงไม่ใช่ค่าสหสัมพันธ์ $\rho$ อย่างที่อาจคิด แต่เป็นการ
กระจายของ $r = \log p_{\text{จริง}} - \log p_{\text{ทำนาย}}$ ต่างหาก เพราะการแปลง
แบบ monotone ต่อ edge คือยังรักษาลำดับของแต่ละ edge ไว้ ก็ยังสามารถสลับอันดับของ
\emph{เส้นทาง} ได้อยู่ดี ตัวอย่างเช่น เส้นทางที่มี 2 edge ซึ่งแต่ละเส้น $p=0.9$ จะได้ต้นทุนรวม
เทียบเท่า $0.81$ ซึ่งชนะเส้นทางที่มี 1 edge ที่ $p=0.8$ แต่ถ้าแปลงค่าแบบ $0.9 \mapsto 0.5$
และ $0.8 \mapsto 0.45$ (ยังคงรักษาลำดับ 0.9 มากกว่า 0.8 ไว้) อันดับของสองเส้นทางนี้กลับ
สลับกันทันที

อันดับของเส้นทางจะคงเดิมพอดีก็ต่อเมื่อฟังก์ชันที่ fit เป็น power law ($\hat{p} \propto
p^{k}$) เท่านั้น จึงนำค่ามัธยฐานของ $r$ ออกไปก่อน (ค่านี้คือ $k$) แล้ววัดว่าที่เหลือกระจาย
กว้างแค่ไหน ค่า $r$ ที่วัดนี้มีหน่วยเป็น nats เพราะคำนวณจาก $\log$ ฐาน $e$ (ลอการิทึม
ธรรมชาติ) ไม่ใช่ฐาน 2 แบบ bit ที่คุ้นเคยกันทั่วไป เลือกใช้ฐาน $e$ เพราะสะดวกต่อการแปลง
กลับเป็นตัวคูณบนความน่าจะเป็นโดยตรงด้วย $e^r$ (ตัวอย่างการแปลงกลับอยู่ในย่อหน้าถัดไป)
ตารางที่~\ref{tab:resid} รายงานค่าสัมบูรณ์ $|r|$ จากการทำนายแบบ 5-fold out-of-fold
(แบ่งข้อมูลเป็น 5 ส่วนเท่า ๆ กัน ฝึกโมเดลด้วย 4 ส่วน แล้วทำนายส่วนที่เหลือที่โมเดลไม่เคย
เห็น สลับไปจนครบทั้ง 5 ส่วน วิธีนี้ทำให้ได้ค่าทำนายของ CVE ทุกตัวโดยไม่มีตัวไหนถูกโมเดล
``จำ'' มาก่อนเลย) บน CVE ทั้ง 46{,}360 รายการ โดยแยกกลุ่มที่ EPSS สูงที่สุด 10\% ออกมา
ดูต่างหาก เพราะ edge ที่มีโอกาสสูงคือ edge ที่มักตัดสินว่าเส้นทางไหนถูกที่สุด

เทียบเท่า $e^{1.938} \approx 6.95$ เท่าบน $p(e)$ ขณะที่แถบการรบกวน $\pm 10$--$50\%$ ที่

เท่า) พูดอีกแบบคือ แถบที่กำหนดไว้ในข้อเสนอแคบกว่าความคลาดเคลื่อนที่วัดได้จริงประมาณ

4--10 เท่า แล้วแต่เปอร์เซ็นไทล์'' ไม่ใช่ ``หนึ่ง order of magnitude'' ลอย ๆ เพราะตัวเลขนั้น
เป็นจริงเฉพาะที่เปอร์เซ็นไทล์ที่ 90 เท่านั้น

\section{การเปรียบเทียบ Dominator Tree กับ Weighted Min-Cut (วัตถุประสงค์ข้อ 3)}\label{sec:eval-cut}

วัตถุประสงค์ข้อ 3 ถามว่าจุดตัดสองนิยามที่ออกแบบไว้ในหัวข้อ~\ref{sec:design-chokepoint}
และ~\ref{sec:design-mincut} ให้คำตอบตรงกันหรือไม่ นิยามแรกคือ post-dominator เป็น
วิธีเชิงโครงสร้างล้วน ไม่อ่านน้ำหนักเลย คืนเซตของ node ที่อยู่บน\emph{ทุก}เส้นทาง นิยามที่สอง
คือ weighted node min-cut คืนชุด node ที่ตัดแล้วผู้โจมตีไปไม่ถึงเป้าหมาย โดยมีต้นทุนรวม
ต่ำที่สุด หัวข้อนี้เทียบสองนิยามนี้บนกราฟชุดเดียวกันทั้ง 864 กราฟถ่วงน้ำหนัก

\subsection{จุดตัดเชิงโครงสร้างเป็นกรณีสุดขั้วของชั้นความน่าจะเป็น}\label{sec:eval-cut-extreme}

ก่อนเทียบตัวเลขจริง มีความสัมพันธ์หนึ่งที่ควรรู้ไว้ก่อน เพราะช่วยอธิบายว่าทำไมสองวิธีจึงควร
ใกล้เคียงกัน: post-dominator set พิสูจน์ได้ว่าเท่ากับเซต $\{v : \Delta(v) = \infty\}$ พอดี
(คือเซตของ node ที่ถ้าลบแล้วผู้โจมตีไปไม่ถึงเป้าหมายเลย ต้นทุนจึงเพิ่มเป็นอนันต์) นั่นแปลว่า
จุดตัดเชิงโครงสร้างไม่ใช่วิธีที่แยกขาดจากชั้นความน่าจะเป็นเลย แต่เป็นกรณีสุดขั้วของมันเอง
คุณสมบัตินี้ตรวจสอบแล้วด้วย brute force บนกราฟสุ่ม 300 กราฟ
(\texttt{tests/test\_bruteforce.py}) และพบว่าจำนวน node ที่ $\Delta(v)=\infty$ เท่ากับ
ขนาดของ global set ทุกกราฟจริง ๆ

ไม่ใช่ค่าหลักของการเปรียบเทียบ
\end{enumerate}

ตารางที่~\ref{tab:seg} ให้คำตอบที่ชัดเจน: micro-segmentation ให้จุดตัดที่การันตีได้บ่อย
กว่าอีกสองแบบอย่างมีนัยสำคัญ (ช่วงความเชื่อมั่นของมันไม่ซ้อนทับกับอีกสองแบบเลย) ซึ่งตรง
กับสัญชาตญาณ: เครือข่ายที่แบ่งส่วนละเอียดบีบให้ทุกเส้นทางต้องลอดผ่าน node เชื่อมเพียงไม่
กี่ตัว node เหล่านั้นจึงกลายเป็นคอขวดที่ทุกเส้นทางต้องผ่านจริง ๆ ส่วน flat และ 3-tier มี
เส้นทางสำรองมากเกินกว่าจะมีจุดตัดร่วมที่ทุกคู่ต้องผ่านเหมือนกันหมด

อย่างไรก็ตาม ถึงแม้ micro จะให้ผลดีที่สุด ก็ยังมีจุดตัดเพียง 22\% ของกราฟในกลุ่มนั้นเท่านั้น
การพึ่งจุดตัดที่การันตีได้จึงใช้ได้จริงเฉพาะส่วนน้อยของกราฟ ส่วนที่เหลือต้องใช้การจัดอันดับ
$\Delta(v)$ (หัวข้อ~\ref{sec:design-chokepoint}) แทนการหาเซตที่การันตีได้แบบเข้มงวด

มีข้อสังเกตด้านความแปรปรวนที่ควรบันทึกไว้ด้วย: grid รุ่นก่อนของโครงงานนี้ (135 โครงสร้าง
ใช้ seed คนละชุด) เคยให้ค่า micro-segmentation สูงถึง 44\% ตัวเลขที่ต่างกันมากขนาดนี้
ระหว่างสองรันย้ำว่าสัดส่วนประเภทนี้มีความแปรปรวนสูง เมื่อจำนวนกราฟที่เข้าเงื่อนไขมีน้อย
จึงต้องรายงานเป็นจำนวนกราฟพร้อมช่วงความเชื่อมั่นเสมอ ไม่ใช่ตัวเลขจุดเดียวแบบที่เคยทำ

\section{ความเสถียรของอันดับเมื่อ edge ขาดหาย}\label{sec:eval-drop}

ถ้าอันดับทนทานต่อ \emph{น้ำหนัก} ที่ผิด แล้วมันทนทานต่อ \emph{ข้อมูลที่ขาดหาย} ด้วยหรือไม่
เพราะในโลกจริงการเก็บข้อมูลเครือข่ายมักไม่ครบ 100\% การทดลองนี้จำลองสถานการณ์นั้น
ด้วยการลบ edge แบบสุ่ม 5, 10 และ 20\% ของกราฟ ข้อแตกต่างสำคัญจากการรบกวนน้ำหนัก
ในหัวข้อก่อนคือ การลบ edge เปลี่ยน\emph{โครงสร้าง}ของกราฟโดยตรง และอาจตัดบางคู่
(entry, target) ออกจากกันไปเลยทั้งคู่ ไม่ใช่แค่เปลี่ยนต้นทุนของเส้นทางที่มีอยู่แล้ว

ได้ตั้งใจ: ส่วนหนึ่งคืออันดับเปลี่ยนเพราะต้นทุนเส้นทางเปลี่ยนจริง ๆ อีกส่วนหนึ่งคือคู่ (entry,
target) บางคู่หลุดจากกันไปเลย ทำให้ node ที่เคยติดอันดับหายไปโดยสิ้นเชิงแบบที่ไม่เกี่ยวกับ
คุณภาพน้ำหนักเลย เพื่อแยกสองผลนี้ออกจากกัน คอลัมน์ ``เงื่อนไข'' จึงคำนวณเฉพาะกราฟที่ยัง
คงคู่ (entry, target) ไว้ได้อย่างน้อย 90\% หลังลบ edge แล้ว แม้การกรองแบบนี้จะทำให้
Jaccard@5 สูงขึ้นมาก (0.749 เทียบกับ 0.493 ที่ลบ 5\%) แต่ค่าก็ยังลดลงต่อเนื่องเมื่อลบ edge
มากขึ้นอยู่ดี และจำนวนกราฟที่ผ่านเงื่อนไขนี้ลดฮวบเหลือเพียง 17 กราฟที่ระดับลบ 20\% ทำให้
ตัวเลขที่ระดับนั้นมีความแปรปรวนสูงมาก (ช่วงความเชื่อมั่น 95\% กว้างถึง 0.32--0.66)

เมื่อเทียบตัวเลขจากทั้งสองหัวข้อนี้เข้าด้วยกัน จะเห็นข้อสรุปที่สำคัญ: edge ที่ขาดหายกระทบ
อันดับรุนแรงกว่าน้ำหนักที่คลาดเคลื่อนมาก ลบ edge เพียง 5\% ก็ลด Jaccard@5 ลงมากกว่า
การรบกวนน้ำหนักถึง 8 เท่าของ residual จริงเสียอีก (0.493 เทียบกับ 0.912 ในหัวข้อก่อน)
ข้อสรุปเชิงปฏิบัติคือ ความสมบูรณ์ของข้อมูล (การเก็บ edge ให้ครบ) สำคัญกว่าความแม่นยำ
ของน้ำหนักบน edge ที่เก็บมาได้แล้วเสียอีก

\section{การเปรียบเทียบโมเดลน้ำหนัก 4 แบบ}\label{sec:eval-models}

ช่วยให้อันดับจุดตัดดีกว่าการใช้ CVSS เฉย ๆ หรือไม่ หัวข้อนี้เทียบอันดับจุดตัดที่ได้จากน้ำหนัก

ที่แฝงอยู่ในน้ำหนัก

ตารางนี้จึงวัดได้แค่\emph{ความต่างกันของอันดับ}ระหว่างสองน้ำหนักเท่านั้น ไม่ใช่ความถูกต้อง
การที่ EPSS ใกล้เคียงกับ CVSS มากกว่าใกล้เคียงกับ random อยู่เล็กน้อย พอจะบ่งชี้ได้ว่าทั้ง
สองโมเดลที่มีข้อมูลจริงรองรับให้อันดับที่คล้ายกันในระดับหนึ่ง แต่ความคล้ายนั้นเมื่อเทียบกับ
null model แล้วมีขนาดเล็กมาก สรุปตามหลักการที่วางไว้ตั้งแต่ต้นโครงงานว่า
การทดลองนี้วัดได้เพียง disagreement rate และความเสถียรของอันดับเท่านั้น ไม่ใช่ความ
แม่นยำ

เส้นทางที่แท้จริงที่สุดคือเส้นไหน ขณะที่ \texttt{top\_path\_same} นับเฉพาะเส้นทางเดียวที่
ถูกที่สุดเท่านั้น เมื่อสองเส้นทางมีต้นทุนใกล้กันมาก การสลับตำแหน่งกันทำได้ง่ายโดยที่อันดับ
node โดยรวมไม่เปลี่ยนเลย กล่าวโดยสรุป การใช้ fit แทน EPSS จริงปลอดภัยสำหรับงานจัด
อันดับจุดตัด แต่ไม่ปลอดภัยสำหรับการชี้ว่า ``เส้นทางโจมตีที่เป็นไปได้มากที่สุด'' คือเส้นไหน
เพียงเส้นเดียว

ผลลัพธ์นี้ยืนยันทิศทางที่คาดไว้ในหัวข้อ~\ref{sec:eval-pe-order} (ที่ว่าเงื่อนไขจำเป็นของการ
รักษาอันดับคือการกระจายของ $|r|$ ในหน่วย log) แต่ก็แสดงด้วยว่าเงื่อนไขนั้นเข้มงวดเกินไป
สำหรับ\emph{อันดับ node} โดยเฉพาะ: แม้ $|r|$ เฉลี่ย 1 nat จะมากกว่าแถบ $\pm10$--$50\%$
ของข้อเสนอหลายเท่า อันดับ node ก็ยังรอดอยู่ดี เพราะอันดับ node พึ่งเพียงว่า node ใดอยู่บน
เส้นทางถูกสุด\emph{ของคู่ใดคู่หนึ่ง}เท่านั้น ไม่ได้ขึ้นกับว่าเส้นทางถูกสุดเพียงเส้นเดียวคือเส้นใด
ข้อควรระวังคือการทดลองนี้ครอบคลุมเฉพาะกราฟขนาด $n=200$ เท่านั้น ไม่ใช่ทั้ง grid

\section{สัดส่วนเส้นทางที่ข้ามโดเมน}\label{sec:eval-cross}

กลับมาที่คำถามของข้อเสนอโครงงานโดยตรง: เส้นทางโจมตีที่อันตรายที่สุดวิ่งผ่านขอบเขต
on-prem--cloud ในสัดส่วนเท่าใด หัวข้อนี้วัดสองค่าต่อคู่ (entry, target) ที่ไปถึงกันได้ ค่าแรก
คือ \texttt{cheapest\_cross\_share} คือสัดส่วนที่เส้นทางถูกสุด (ต้นทุนต่ำสุดตาม
$-\log p$) ใช้ edge ข้ามโดเมนอย่างน้อยหนึ่งเส้น ค่าที่สองคือ
\texttt{cross\_required\_share} คือสัดส่วนที่คู่นั้น\emph{ต้อง}ข้ามโดเมนเท่านั้นจึงจะไป
ถึงกันได้ ถ้าตัด edge ข้ามโดเมนทั้งหมดออก คู่นั้นจะไปถึงกันไม่ได้อีกเลย ทั้งสองค่าวัด
บนน้ำหนัก EPSS บนกราฟ 216 โครงสร้าง

ก่อนอ่านตัวเลข ต้องรู้ข้อจำกัดหนึ่งก่อน: เนื่องจาก entry ทุกตัวอยู่ฝั่ง on-prem โดยการ
ออกแบบของตัวสร้างกราฟเองตั้งแต่ต้น (หัวข้อ~\ref{sec:design-gen}) คู่ที่มี target อยู่ฝั่ง
cloud จึง\emph{ต้อง}ข้ามโดเมนเสมอโดยโครงสร้าง (ได้ 100\% ทั้งสองค่าโดยอัตโนมัติ ไม่มี
ทางเป็นอื่น) ตัวเลขที่มีความหมายจริงจึงอยู่ที่คู่ซึ่ง target เป็น on-prem ด้วยกันเท่านั้น เพราะ
กรณีนั้นการข้ามโดเมนเป็นทางเลือก ไม่ใช่ข้อบังคับ

กรณีเท่านั้น และมีเพียง 11.8\% เท่านั้นที่\emph{ไม่มีทางเลือกอื่น}นอกจากข้ามโดเมน พูดอีกแบบ
คือ ส่วนใหญ่ของเส้นทางอันตรายในเครือข่ายเดียวกันไม่จำเป็นต้องพึ่งพาการเชื่อมต่อข้าม
โดเมนเลย

ตัวเลข 11.8\% นี้ต้องอ่านอย่างระมัดระวัง เพราะส่วนใหญ่มาจากกราฟแบบ micro-segmentation
เพียงแบบเดียว (44.7\% เทียบกับ 4.8\% ของ 3-tier และ 3.0\% ของ flat) ที่เป็นแบบนี้เพราะ
ขั้นตอนซ่อมกราฟ (repair, หัวข้อ~\ref{sec:design-gen}) ไม่ใช่เพราะโครงสร้างธรรมชาติล้วน ๆ
เมื่อ micro-segmentation ตัดทุกเส้นทางภายในออกจนบางคู่ไปไม่ถึงกัน ตัวสร้างกราฟจะเติม
edge แบบ VPN/Direct Connect เข้าไปซ่อม edge แบบนี้ถูกจัดเป็น \texttt{domain="cross"}
เสมอ ตัวเลข 11.8\% จึงสะท้อนพฤติกรรมของตัวซ่อมกราฟบางส่วน ไม่ใช่คุณสมบัติที่พบใน
เครือข่ายจริงล้วน ๆ ต้องระบุข้อจำกัดนี้กำกับไว้ทุกครั้งที่อ้างถึงตัวเลขนี้ (ดูหัวข้อ~
\ref{sec:eval-limits}) นอกจากนี้สัดส่วนยังเพิ่มขึ้นตามความหนาแน่นของ edge ข้ามโดเมน
ที่กำหนดไว้ (low 12.2\%, med 18.2\%, high 22.1\%) ตรงตามสัญชาตญาณ: ยิ่งมี edge
ข้ามโดเมนให้เลือกมาก เส้นทางถูกสุดก็ยิ่งมีโอกาสผ่าน edge เหล่านั้นมากขึ้นตามไปด้วย

บัญชี AWS Academy Learner Lab บล็อกการสร้าง IAM resource ทั้งหมด (รายละเอียดอยู่ใน
ภาคผนวก~\ref{app:deviation}) ผลที่ตามมาคือกราฟ lab นี้ไม่มี edge ชนิด CVE แม้แต่เส้น
เดียว จึงยังไม่ได้ทดสอบฝั่ง EPSS ของวัตถุประสงค์ข้อ 2 ด้วยข้อมูลจริง ทดสอบได้เฉพาะฝั่ง
misconfiguration และ deterministic เท่านั้น นอกจากนี้ฝั่ง on-prem ก็ไม่ได้ผ่าน
Cartography/Neo4j ด้วย (เพราะ Cartography รองรับเฉพาะ cloud) แต่อ่านข้อมูลตรงจาก
\texttt{docker exec}/\texttt{nmap} แทน

แม้จะมีข้อจำกัดเหล่านี้ edge ข้ามโดเมนเส้นเดียวในกราฟนี้ (\texttt{aws-key-on-host}) ก็
ยังได้รับการยืนยันอย่างน่าเชื่อถือ เพราะต้องการหลักฐานจากสองแหล่งข้อมูลอิสระที่ต้องตรงกัน
คือไฟล์ credential บนโฮสต์ และ node ที่ Cartography ค้นพบเองจากฝั่ง cloud ความน่าเชื่อ
ถือของกฎนี้ทดสอบแล้วจริง: เมื่อลองแก้ไข key id บนโฮสต์ให้ไม่ตรงกับฝั่ง cloud exporter
ปฏิเสธสร้าง edge นั้นทันที ซึ่งยืนยันว่า edge ข้ามโดเมนนี้เป็นข้อเท็จจริงที่ตรวจสอบได้จริง ไม่ใช่
ข้อเท็จจริงที่ปลูกไว้ฝ่ายเดียว

\section{อภิปรายผลและภัยต่อความตรงของผล}\label{sec:eval-threats}

หัวข้อนี้รวบรวมปัจจัยที่อาจทำให้ตีความผลข้างต้นผิดพลาดได้ (threats to validity) เรียง
ตามความสำคัญ แต่ละข้อถูกวัดหรือทดสอบจริงระหว่างการตรวจทานโครงงาน ไม่ใช่ข้อสงสัย
ลอย ๆ ที่คิดขึ้นมาเฉย ๆ

\begin{enumerate}[leftmargin=1.6em]

\item \textbf{ตัวสร้างกราฟให้โครงสร้างแบบโซ่ (serial), ไม่ใช่เครือข่ายจริง}
ในหัวข้อ~\ref{sec:eval-noise} อันดับ node ทนทานต่อน้ำหนักที่ผิดมาก จนแม้แต่น้ำหนักแบบ
สุ่มล้วน (\texttt{random}) ก็ยังให้อันดับใกล้เคียงกับ EPSS การที่ null model ให้ผลใกล้เคียง
กับโมเดลที่มีข้อมูลจริงขนาดนี้บ่งชี้ว่าอันดับถูกกำหนดโดย\emph{ตำแหน่งของ node ใน
โครงสร้าง}เป็นหลัก ไม่ใช่คุณภาพของน้ำหนัก และนี่เป็นคุณสมบัติของกราฟที่สร้างขึ้น (ซึ่งส่วน
ใหญ่มีเส้นทางสำรองน้อย) ยังไม่ได้พิสูจน์เลยว่าเครือข่ายไฮบริดจริงก็เป็นเช่นนั้นด้วย

\item \textbf{สถิติ per-target/per-pair ที่ไม่ว่าง 100\% เป็น artifact ของตัวสร้างกราฟ}
ตามที่กล่าวไว้ในหัวข้อ~\ref{sec:eval-cut-defs} เพราะ target แต่ละตัวมี in-edge เดียวโดย
โครงสร้าง ตัวเลขนี้จึงไม่ควรนำไปใช้เป็นหลักฐานว่าเครือข่ายจริงมีจุดตัดต่อ target เสมอ

\item \textbf{สัดส่วน global choke point แปรปรวนสูงระหว่างรันสองครั้ง} grid รุ่นก่อน (135
โครงสร้าง ใช้ seed คนละชุด) เคยให้ค่า micro-segmentation ที่ 44\% ขณะที่ grid สุดท้าย
(216 โครงสร้าง) ให้ 22\% ทั้งที่ใช้ตัวสร้างกราฟตัวเดียวกันเป๊ะ ความต่างนี้ย้ำว่าต้องรายงาน
ตัวเลขกลุ่มนี้พร้อมช่วงความเชื่อมั่นเสมอ ไม่ใช่ตัวเลขจุดเดียวลอย ๆ (ตารางที่~\ref{tab:seg})

\item \textbf{สมมติฐาน edge independence และ OR-semantics ทำให้ผล Dijkstra เป็น
เพียงขอบเขตล่างของต้นทุนผู้โจมตี} (lower bound) ต้นทุนจริงไม่มีทางแพงกว่านี้ มีแต่จะ
เท่ากันหรือถูกกว่า ตามที่อธิบายไว้ในหัวข้อ~\ref{sec:design-model} ไม่ใช่ความน่าจะเป็นที่จะ
ถูกเจาะจริง ($P(\text{compromise})$) เพราะภายใต้ OR-semantics ยังมีหลายเส้นทางที่ไปถึง
เป้าหมายเดียวกันได้ ความน่าจะเป็นที่แท้จริงจึงต้องมากกว่าความน่าจะเป็นของเส้นทางเดียวที่ถูกที่สุด

\item\label{item:threat-pscale} \textbf{สเกลของ $p$ ระหว่าง edge ประเภท fitted/EPSS
กับ deterministic ไม่ใช่ความหมายเดียวกัน} EPSS วัด ``โอกาสถูกโจมตีที่ไหนสักแห่งในโลก''
ไม่ใช่ ``โอกาสสำเร็จเมื่อยืนอยู่ต้นทางแล้ว'' ขณะที่ edge เชิงโครงสร้างมี $p=1$ เสมอ การผสม
สองความหมายนี้ในกราฟเดียวกันทำให้ Dijkstra เลือกเส้นทางตามน้ำหนักฝั่งที่ถูก calibrate
เป็นหลัก การตัดสินใจของโครงงานนี้ (ยืนยันแล้ว) คือคงรูปแบบนี้ไว้ พร้อมรายงาน sensitivity
analysis กำกับ แทนที่จะแยกสเกลออกจากกัน (รายละเอียดอยู่ในภาคผนวก~\ref{app:deviation})

\item \textbf{ไม่มีค่าจริง (ground truth) บนกราฟจำลอง} ดังนั้นหัวข้อ~\ref{sec:eval-models}
วัดได้เพียงความต่างระหว่างอันดับของสองโมเดลน้ำหนักเท่านั้น ไม่ใช่ว่าโมเดลใด ``ถูกต้อง
กว่า'' อีกโมเดลหนึ่ง

\item \textbf{ตัวอย่างข้อมูลสำหรับ fit ไม่ใช่การสุ่ม CVE} ตามที่กล่าวไว้ในหัวข้อ~
\ref{sec:eval-pe-data} แต่เป็นบล็อกต่อเนื่องจาก NVD ซึ่งปีกระจายไม่สม่ำเสมอ (ไม่มีปี 2016
เลย) และค่า $R^2$ ที่รายงาน (0.219) มาจากการแบ่งข้อมูลทดสอบแบบสุ่มราย CVE ซึ่งมอง
โลกในแง่ดีกว่าการใช้งานจริง: เมื่อกันทั้งหน้า NVD ออกแทน $R^2$ ลดเหลือ 0.156 และเมื่อ
ฝึกด้วยข้อมูลถึงปี 2022 แล้วทดสอบกับปี 2023 เป็นต้นไป $R^2$ ติดลบไปเลย ($-0.863$) แม้
Spearman $\rho$ จะยังอยู่ที่ 0.542 (ตรวจสอบแล้วด้วย \texttt{scripts/audit\_data.py})

\end{enumerate}

\section{ข้อจำกัด}\label{sec:eval-limits}
\begin{itemize}[leftmargin=1.4em]
\item \textbf{ไม่มี AND-node} โมเดลนี้ใช้ OR-semantics ล้วน ตามที่ประกาศไว้ตั้งแต่ต้น
การโจมตีที่ต้องอาศัยเงื่อนไขหลายอย่างพร้อมกัน (เช่น AND-node ของ MulVAL) จึงไม่ได้ถูก
แสดงในกราฟเลย
\item \textbf{lab ไม่มี edge ชนิด CVE} เพราะแทนที่ Nessus ด้วย \texttt{nmap} ซึ่งให้แค่
ข้อมูลการเข้าถึงพอร์ต การทดสอบฝั่ง EPSS ของวัตถุประสงค์ข้อ 2 บนระบบจริงจึงยังไม่เกิดขึ้น
\item \textbf{lab ฝั่ง on-prem ไม่ผ่าน Cartography/Neo4j} แต่อ่านข้อมูลตรงจาก
\texttt{docker exec}/\texttt{nmap} แทน เพราะ Cartography รองรับเฉพาะ cloud provider
\item \textbf{AWS จริงใช้ไม่ได้} บัญชี AWS Academy Learner Lab บล็อกการสร้าง IAM
resource ทั้งหมด (ภาคผนวก~\ref{app:deviation}) lab จึงต้องรันบน LocalStack แทน
\item \textbf{3 กลุ่มคลาส misconfiguration มีค่า $p$ เท่ากันเป๊ะ} เพราะตกอยู่ใน CVSS
cell เดียวกัน (\texttt{iam-trust-wildcard-principal}/\texttt{cicd-oidc-broad-sub}/
\texttt{federated-group-overbroad-role}; \texttt{iam-passrole-excess-privilege}/
\texttt{stale-service-account-cred}; \texttt{unauth-internal-service}/
\texttt{weak-ssh-credentials}) จึงแยกด้วยน้ำหนักไม่ได้เลย แม้แนวคิดจะต่างกันก็ตาม
\item \textbf{กราฟจำลองมีโครงสร้างแบบโซ่เป็นส่วนใหญ่} ยังไม่ได้ตรวจสอบกับ topology ของ
เครือข่ายไฮบริดจริงเลยว่าใกล้เคียงกันเพียงใด
\end{itemize}
