\section{ผลการประมาณค่า $p(e)$ จาก CVSS (วัตถุประสงค์ข้อ 2)}

edge ที่เป็น misconfiguration ไม่มี CVE จึงไม่มีคะแนน EPSS ให้ใช้โดยตรง
โครงงานนี้จึงกำหนดเวกเตอร์ CVSS ให้แต่ละคลาสของ misconfiguration ตาม rubric (ภาคผนวก ก)
แล้วใช้ฟังก์ชันที่เรียนรู้ความสัมพันธ์ระหว่างเวกเตอร์ CVSS กับคะแนน EPSS ของ CVE จริง
แปลงเวกเตอร์นั้นเป็นค่าความน่าจะเป็น $p(e)$
หัวข้อนี้รายงานว่าฟังก์ชันดังกล่าวแม่นเพียงใด
เพราะความคลาดเคลื่อนของ $p(e)$ ส่งผลต่ออันดับเส้นทางโดยตรง

และคะแนน EPSS จาก snapshot วันที่ 2026-08-26 โดยเป็น CVE ที่เผยแพร่ระหว่าง 2017-03-20 ถึง 2026-08-06

\subsection{ความคลาดเคลื่อนในหน่วย log}

เนื่องจากต้นทุนของเส้นทางคือผลรวมของ $-\log p$ บน edge
ค่าที่กำหนดว่าอันดับเส้นทางเปลี่ยนหรือไม่คือการกระจายของ
$r = \log p_{\text{จริง}} - \log p_{\text{ทำนาย}}$
ไม่ใช่ค่าสหสัมพันธ์ $\rho$ เพราะการแปลงแบบ monotone ต่อ edge สามารถสลับอันดับของเส้นทางได้
(เส้นทางที่มี 2 edge ที่ $p=0.9$ ได้ $0.81$ ชนะเส้นทางที่มี 1 edge ที่ $p=0.8$
แต่ถ้า map $0.9 \mapsto 0.5$ และ $0.8 \mapsto 0.45$ อันดับจะกลับกัน)
อันดับของเส้นทางคงเดิมพอดีเมื่อฟังก์ชันเป็น power law $\hat{p} \propto p^{k}$
จึงนำค่ามัธยฐานของ $r$ ออก (ซึ่งคือค่า $k$) แล้ววัดความกว้างที่เหลือ
ตารางที่~\ref{tab:resid} รายงานค่าสัมบูรณ์ $|r|$ จากการทำนายแบบ 5-fold out-of-fold บน CVE ทั้ง 46{,}360 รายการ
โดยแยกกลุ่มที่ EPSS สูงที่สุด 10\% ออกมาต่างหาก เพราะ edge ที่ตัดสินเส้นทางคือ edge ที่มีโอกาสสูง

และการรายงานค่า pooled เพียงค่าเดียว (0.587) จะทำให้ฟังก์ชันดูแม่นเกินจริง
ค่า 1.938 nats เทียบเท่าตัวคูณ $e^{1.938} \approx 6.95$ เท่าบน $p(e)$
ขณะที่แถบการรบกวน $\pm 10$--$50\%$ ในข้อเสนอโครงงานมีขนาดมากสุดเพียง $\log 1.5 \approx 0.405$ nats (1.5 เท่า)
แถบที่กำหนดไว้จึงแคบกว่าที่วัดได้ประมาณ 4.8 เท่าที่มัธยฐาน และ 9.8 เท่าที่เปอร์เซ็นไทล์ที่ 90
(ในหน่วย log) ข้อสรุปที่ถูกต้องจึงเป็น ``แคบกว่า 4--10 เท่า แล้วแต่เปอร์เซ็นไทล์''
ไม่ใช่ ``หนึ่ง order of magnitude'' ซึ่งเป็นจริงเฉพาะที่เปอร์เซ็นไทล์ที่ 90

\section{การเปรียบเทียบ Dominator Tree กับ Weighted Min-Cut (วัตถุประสงค์ข้อ 3)}

วัตถุประสงค์ข้อ 3 ถามว่าจุดตัดสองนิยามให้คำตอบตรงกันหรือไม่ นิยามแรกคือ post-dominator
ซึ่งเป็นโครงสร้างล้วน ไม่อ่านน้ำหนัก และคืนเซตของ node ที่อยู่บน\emph{ทุก}เส้นทาง
นิยามที่สองคือ weighted node min-cut ซึ่งคืนชุด node ที่ตัดแล้วผู้โจมตีไปไม่ถึงเป้าหมาย
โดยมีต้นทุนรวมต่ำสุด การเทียบสองนิยามนี้ทำบนกราฟชุดเดียวกันทั้ง 864 กราฟถ่วงน้ำหนัก

\subsection{สามนิยามของจุดตัด}

ก่อนเทียบกับ min-cut ต้องแยกให้ชัดว่า ``จุดตัด'' หมายถึงนิยามใด เพราะทั้งสามให้เซตที่ต่างกัน

\toprule
นิยาม & กราฟที่เซตไม่ว่าง & ขนาดเซตเฉลี่ย \\

นิยาม global เข้มที่สุด จุดตัดต้องอยู่บนทุกเส้นทางของทุกคู่ จึงพบเพียง 18 จาก 216 โครงสร้าง (8.3\%)
ส่วน per-target และ per-pair ไม่ว่าง 100\% ซึ่ง \textbf{เป็น artifact ของตัวสร้างกราฟ ไม่ใช่ผลต่อเครือข่ายจริง}
ในกราฟที่สร้างขึ้น target แต่ละตัวมี in-edge เพียงเส้นเดียวโดยโครงสร้าง node ต้นทางของ edge นั้นจึง
ครอบทุกเส้นทางที่เข้าถึง target เสมอ ค่า 100\% จึงสะท้อนวิธีสร้างกราฟ ไม่ใช่คุณสมบัติของเครือข่ายจริง
รายงานนี้จึงใช้นิยาม global เป็นพาดหัว และกำกับข้อจำกัดนี้ไว้ทุกที่ที่อ้างถึง per-target/per-pair

\subsection{จุดตัดเชิงโครงสร้างเป็นกรณีสุดขั้วของชั้นความน่าจะเป็น}

post-dominator set พิสูจน์ได้ว่าเท่ากับ $\{v : \Delta(v) = \infty\}$ นั่นคือ node ที่ลบแล้ว
ผู้โจมตีไปไม่ถึงเป้าหมายเลย (ต้นทุนเพิ่มเป็นอนันต์) จุดตัดเชิงโครงสร้างจึงไม่ใช่วิธีที่แยกจาก
ชั้นความน่าจะเป็น แต่เป็นกรณีสุดขั้วของมัน คุณสมบัตินี้ตรวจด้วย brute force บนกราฟสุ่ม 300 กราฟ
(\texttt{tests/test\_bruteforce.py}): จำนวน node ที่ $\Delta(v)=\infty$ เท่ากับขนาดของ global set ทุกกราฟ

\subsection{ความตรงกันของ dominator กับ min-cut}

บนเซตว่างมีค่า 1 โดยปริยาย ไม่ได้บอกอะไรเกี่ยวกับสองนิยาม) min-cut รายงานสาม capacity ตามการตัดสินใจ
ตารางที่~\ref{tab:cut} แสดงสัดส่วนที่ node ใน min-cut เป็นสมาชิกของ dominator set ด้วย

ผลสำคัญมีสามข้อ ข้อแรก capacity แบบ \texttt{unit} ซึ่งนับจำนวน node ที่ต้องตัด ตรงกับ dominator set
100\% เป็นผลที่ควรเป็น เพราะทั้งคู่วัดในหน่วยเดียวกันและ dominator ไม่อ่านน้ำหนัก

แต่ลดเหลือ \textbf{72\% เมื่อใช้น้ำหนัก EPSS} กล่าวคือใน 28\% ของกรณี min-cut ที่ถ่วงด้วย EPSS
เลือก node ที่ไม่ใช่ dominator เพราะ node นั้นเป็นคอขวดของ\emph{ความน่าจะเป็น} แม้ไม่ได้อยู่บนทุกเส้นทาง
นี่คือข้อค้นพบหลักของวัตถุประสงค์ข้อ 3 ที่น้ำหนักเชิงประจักษ์ให้คำตอบต่างจากโครงสร้างล้วน
ข้อสาม capacity แบบ \texttt{cost} ($-\log p$) เสื่อม (degenerate) เพราะ edge เชิงโครงสร้างมี $p=1$ จึง $w=0$
node ที่เข้าถึงได้ฟรีจึงถูกตัดด้วยต้นทุนศูนย์ min-cut ยุบไปที่เซตต้นทุนศูนย์ที่เลือกโดยพลการ
ยืนยันด้วยสัดส่วน cut ที่มีต้นทุนรวมเป็นศูนย์พอดีถึง 77\% ของแถว จึงรายงาน \texttt{cost} ไว้เป็น
คอลัมน์ sensitivity เท่านั้น ไม่ใช่ค่าหลัก

\section{สัดส่วนเส้นทางที่ข้ามโดเมน}

ข้อเสนอโครงงานถามว่าเส้นทางโจมตีที่อันตรายที่สุดวิ่งผ่านขอบเขต on-prem--cloud ในสัดส่วนเท่าใด
หัวข้อนี้วัดสองค่าต่อคู่ (entry, target) ที่ไปถึงกันได้: \texttt{cheapest\_cross\_share} คือสัดส่วนที่
เส้นทางถูกสุด (ต้นทุนต่ำสุดตาม $-\log p$) ใช้ edge ข้ามโดเมนอย่างน้อยหนึ่งเส้น และ
\texttt{cross\_required\_share} คือสัดส่วนที่คู่นั้น\emph{ต้อง}ข้ามโดเมน — ถ้าตัด edge ข้ามโดเมน
ทั้งหมดออกแล้วคู่นั้นไปถึงกันไม่ได้เลย ทั้งสองวัดบนน้ำหนัก EPSS บนกราฟ 216 โครงสร้าง

เนื่องจาก entry ทุกตัวอยู่ฝั่ง on-prem โดยการออกแบบของตัวสร้างกราฟ (หัวข้อ 3.4) คู่ที่มี
target อยู่ฝั่ง cloud จึง\emph{ต้อง}ข้ามโดเมนเสมอโดยโครงสร้าง (100\% ทั้งสองค่า) ตัวเลขที่มี
ความหมายจึงอยู่ที่คู่ซึ่ง target เป็น on-prem ด้วยกัน ซึ่งการข้ามโดเมนเป็นทางเลือก ไม่ใช่ข้อบังคับ

สำหรับคู่ที่ target เป็น on-prem ด้วยกัน เส้นทางถูกสุดใช้ edge ข้ามโดเมนเพียง 17.5\% ของกรณี
และมีเพียง 11.8\% เท่านั้นที่\emph{ไม่มีทางเลือกอื่น}นอกจากข้ามโดเมน กล่าวคือ ส่วนใหญ่ของ
เส้นทางอันตรายในเครือข่ายเดียวกันไม่จำเป็นต้องพึ่งพาการเชื่อมต่อข้ามโดเมนเลย

ตัวเลข 11.8\% นี้ต้องอ่านอย่างระมัดระวัง เพราะส่วนใหญ่มาจากกราฟแบบ micro-segmentation
(44.7\% เทียบกับ 4.8\% ของ 3-tier และ 3.0\% ของ flat) ซึ่งเป็นผลจากขั้นตอนซ่อมกราฟ
(repair, หัวข้อ 3.4): เมื่อ micro-segmentation ตัดทุกเส้นทางภายในออกจนบางคู่ไปไม่ถึงกัน
ตัวสร้างกราฟจะเติม edge แบบ VPN/Direct Connect ซึ่งถูกจัดเป็น \texttt{domain="cross"}
เพื่อซ่อมคู่นั้น ตัวเลข 11.8\% จึงสะท้อนพฤติกรรมของตัวซ่อมกราฟบางส่วน ไม่ใช่คุณสมบัติที่
พบในเครือข่ายจริงล้วน ๆ ต้องระบุข้อจำกัดนี้ไว้ทุกครั้งที่อ้างถึงตัวเลขนี้ (ดูหัวข้อ 5.10)
สัดส่วนยังเพิ่มตามความหนาแน่นของ edge ข้ามโดเมนที่กำหนดไว้ (low 12.2\%, med 18.2\%,
high 22.1\%) ซึ่งเป็นไปตามสัญชาตญาณ: ยิ่งมี edge ข้ามโดเมนให้เลือกมาก เส้นทางถูกสุดก็ยิ่งมี
โอกาสผ่าน edge เหล่านั้น

ปฏิเสธสร้าง edge ทันที (ไม่ใช่ข้อเท็จจริงที่ปลูกไว้ฝ่ายเดียว)
\section{อภิปรายผลและภัยต่อความตรงของผล}

หัวข้อนี้รวบรวมปัจจัยที่อาจทำให้ตีความผลข้างต้นผิด (threats to validity) โดยเรียงตาม
ความสำคัญ แต่ละข้อถูกวัดหรือทดสอบจริงในระหว่างการตรวจทานโครงงาน ไม่ใช่ข้อสงสัยลอย ๆ

\begin{enumerate}[leftmargin=1.6em]

\item \textbf{ตัวสร้างกราฟให้โครงสร้างแบบโซ่ (serial), ไม่ใช่เครือข่ายจริง}
อันดับ node ในหัวข้อ 5.4 ทนทานต่อน้ำหนักที่ผิดมาก แม้แต่น้ำหนักแบบสุ่มล้วน (\texttt{random})
ก็ยังให้อันดับใกล้เคียงกับ EPSS การที่ null model ให้ผลใกล้เคียงกับโมเดลที่มีข้อมูลจริง
ขนาดนี้บ่งชี้ว่าอันดับถูกกำหนดโดย\emph{ตำแหน่งของ node ในโครงสร้าง} เป็นหลัก ไม่ใช่คุณภาพ
ของน้ำหนัก ซึ่งเป็นคุณสมบัติของกราฟที่สร้างขึ้น (ส่วนใหญ่มีเส้นทางสำรองน้อย) ไม่ได้พิสูจน์ว่า
เครือข่ายไฮบริดจริงก็เป็นเช่นนั้น

\item \textbf{สถิติ per-target/per-pair ที่ไม่ว่าง 100\% เป็น artifact ของตัวสร้างกราฟ}
(หัวข้อ 5.2.1) เพราะ target แต่ละตัวมี in-edge เดียวโดยโครงสร้าง ตัวเลขนี้จึงไม่ควรใช้เป็น
หลักฐานว่าเครือข่ายจริงมีจุดตัดต่อ target เสมอ

\item \textbf{สัดส่วน global choke point แปรปรวนสูงระหว่างรันสองครั้ง}
grid รุ่นก่อน (135 โครงสร้าง, seed คนละชุด) ให้ค่า micro-segmentation ที่ 44\% ขณะที่
grid สุดท้าย (216 โครงสร้าง) ให้ 22\% ทั้งที่ใช้ตัวสร้างกราฟตัวเดียวกัน ความต่างนี้ย้ำว่า
ต้องรายงานตัวเลขกลุ่มนี้พร้อมช่วงความเชื่อมั่นเสมอ ไม่ใช่ตัวเลขจุดเดียว (ตารางที่~\ref{tab:seg})

\item \textbf{สมมติฐาน edge independence และ OR-semantics ทำให้ผล Dijkstra เป็นเพียง
lower bound} ของต้นทุนผู้โจมตี ไม่ใช่ความน่าจะเป็นที่จะถูกเจาะจริง ($P(\text{compromise})$)
เพราะภายใต้ OR-semantics มีหลายเส้นทางที่ไปถึงเป้าหมายเดียวกันได้ ความน่าจะเป็นรวมจึง
มากกว่าความน่าจะเป็นของเส้นทางเดียวที่ถูกสุด

\item \textbf{สเกลของ $p$ ระหว่าง edge ประเภท fitted/EPSS กับ deterministic ไม่ใช่
ความหมายเดียวกัน} EPSS วัด ``โอกาสถูกโจมตีที่ไหนสักแห่งในโลก'' ไม่ใช่ ``โอกาสสำเร็จเมื่อยืน
อยู่ต้นทางแล้ว'' ขณะที่ edge เชิงโครงสร้างมี $p=1$ เสมอ การผสมสองความหมายในกราฟเดียว
ทำให้ Dijkstra เลือกเส้นทางตามน้ำหนักฝั่งที่ถูก calibrate เป็นหลัก (การตัดสินใจคงรูปแบบนี้ไว้
พร้อม sensitivity analysis แทนการแยกสเกล — ดูภาคผนวก ง)

\item \textbf{ไม่มีค่าจริง (ground truth) บนกราฟจำลอง} ดังนั้นหัวข้อ 5.6 วัดได้เพียง
ความต่างระหว่างอันดับของสองโมเดลน้ำหนัก ไม่ใช่ว่าโมเดลใด ``ถูกต้องกว่า''

\item \textbf{ตัวอย่างข้อมูลสำหรับ fit ไม่ใช่การสุ่ม CVE} (หัวข้อ 5.1.1) แต่เป็นบล็อกต่อเนื่อง
จาก NVD ปีกระจายไม่สม่ำเสมอ (ไม่มีปี 2016 เลย) และ $R^2$ ที่รายงาน (0.219) มาจากการแบ่ง
ข้อมูลทดสอบแบบสุ่มราย CVE ซึ่งมองโลกในแง่ดีกว่าการใช้งานจริง: เมื่อกันทั้งหน้า NVD ออก
$R^2$ ลดเหลือ 0.156 และเมื่อฝึกด้วยข้อมูลถึงปี 2022 แล้วทดสอบกับปี 2023 เป็นต้นไป $R^2$
ติดลบ ($-0.863$) แม้ Spearman $\rho$ จะยังอยู่ที่ 0.542 (ตรวจด้วย \texttt{scripts/audit\_data.py})

\end{enumerate}

\section{ข้อจำกัด}

\begin{itemize}[leftmargin=1.4em]
\item \textbf{ไม่มี AND-node} โมเดลนี้ใช้ OR-semantics ล้วน ตามที่ประกาศไว้ตั้งแต่ต้น
การโจมตีที่ต้องอาศัยเงื่อนไขหลายอย่างพร้อมกัน (เช่น MulVAL's AND-node) ไม่ได้แสดงในกราฟ
\item \textbf{lab ไม่มี edge ชนิด CVE} เพราะแทนที่ Nessus ด้วย \texttt{nmap} ซึ่งให้แค่ข้อมูล
การเข้าถึงพอร์ต การทดสอบฝั่ง EPSS ของวัตถุประสงค์ข้อ 2 บนระบบจริงจึงยังไม่เกิดขึ้น
\item \textbf{lab ฝั่ง on-prem ไม่ผ่าน Cartography/Neo4j} อ่านข้อมูลตรงจาก \texttt{docker
exec}/\texttt{nmap} แทน เพราะ Cartography รองรับเฉพาะ cloud provider
\item \textbf{AWS จริงใช้ไม่ได้} บัญชี AWS Academy Learner Lab บล็อกการสร้าง IAM resource
ทั้งหมด (ภาคผนวก ง) lab จึงรันบน LocalStack แทน
\item \textbf{3 กลุ่มคลาส misconfiguration มีค่า $p$ เท่ากันเป๊ะ} เพราะตกอยู่ใน CVSS cell
เดียวกัน (\texttt{iam-trust-wildcard-principal}/\texttt{cicd-oidc-broad-sub}/
\texttt{federated-group-overbroad-role}; \texttt{iam-passrole-excess-privilege}/
\texttt{stale-service-account-cred}; \texttt{unauth-internal-service}/\texttt{weak-ssh-credentials})
แยกด้วยน้ำหนักไม่ได้แม้แนวคิดจะต่างกัน
\item \textbf{กราฟจำลองมีโครงสร้างแบบโซ่เป็นส่วนใหญ่} ยังไม่ได้ตรวจสอบกับ topology ของ
เครือข่ายไฮบริดจริงว่าใกล้เคียงกันเพียงใด
\end{itemize}
